# A-111 諸勢力の一括仕官と旗揚げ時の派閥再編確定順序（r786）

## 正本と実ゲームでの経路

r785を基準とした継続監査。`FactionSystem.updateFactions()` が唯一の派閥選出・形成・解散正本であることは維持する。一方、`KunishuSystem.processEndMonth()` の「常陸の不死鳥」等による大名復帰は `executeIndependentRise()` → `getKunishuMembers()` → 配下全員の `AffiliationSystem.joinClan()` → 頭領の `isDaimyo = true` の順に実行していた。`joinClan()` が毎回即時に派閥再編していたため、**まだ大名に就任していない頭領を通常家臣と判定して派閥主へ選び、後で大名になっても派閥主フラグが残る**。取込コマンド成功時も複数の諸勢力配下を1名ずつ `joinClan()` へ渡しており、同一命令中の派閥再編が人数分重複した。また、頭領よりも先に他の配下が名簿に並ぶ旗揚げでは、途中の自動城主選出によって仮の城主任命履歴が1件残ることも再現した。

## 再現と処置

`AffiliationSystem`・`FactionSystem`・`KunishuSystem`・通常の `Clan` モデルを実際に読み込む結合fixtureを追加。頭領・他の派閥主候補・配下2名を持つ諸勢力が空拠点で旗揚げする経路を実行し、r785では4名の仕官のたびに4回再編され、頭領が `isDaimyo && isFactionLeader` になることを確認した。諸勢力4名の取込でも4回再編した。追加の2テストだけが失敗し、修正前の基準1,277件は通過した。

- `AffiliationSystem.joinClan()` の既存の5引数は維持し、第6引数のオプション `deferFactionUpdate`・`deferCastleLordUpdate`・`deferUI` を受けられるようにする。既存の `leaveCastle()`・`enterCastle()`・`updateUI()` にそのまま渡し、同じ状態変更を分岐ごとに実装しない。通常の単独仕官・登用は変更せず従来どおり即時確定する。
- 諸勢力の旗揚げは配下全員を `joinClan()` に通し、その間の派閥再編・城主更新・画面再描画を保留する。頭領の大名就任後に城主を一度だけ確定し、**新家の `updateFactions(newClanId)` を1回だけ**呼び、画面を更新する。
- 諸勢力の取込も全員の仕官・名簿確定後に `updateFactions(playerClanId)` を1回だけ呼ぶ。
- 派閥選出計算・忠誠度計算・役職の正本・兵士合流・外交・城の所有権・ゲームバランス・管理Excel/BIN・セーブ形式を変更しない。通常の単発処理や別種の歴史イベントを根拠なく一括書換しない。

- 変更後 r786: **1,279 passed / 0 failed**（同じ追加テストと全既存テスト）。旗揚げ後の大名と派閥主の非兼任、両経路の再編1回、仮城主任命履歴0件、全員の正規所属移籍を検査。
