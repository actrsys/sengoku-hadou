# r896 野戦移動ハイライトと軍勢情報DOM更新の軽量化監査記録

## 1. 監査対象
- 基準：r895 完全版（`js/field_war.js`）。
- 範囲：`FieldWarManager.updateMap()` の移動範囲描画、`FieldWarManager.updateStatus()` の情報表示時DOM更新、固定野戦画面の初期化・終了時の寿命。
- 禁則：表示結果、移動可否、戦闘計算、乱数の消費、AI判断、演出時間、セーブデータ、正式マニュアル原文を変更しない。

## 2. 発見
- `PHASE_MOVE`・`MOVE_PREVIEW` の移動可能HEXを巡るたび、味方占有位置を `units.some()` で全隊走査していた。占有HEXが複数あると、同一ターンの敵配列、現在位置から敵への距離、スキル判定用味方配列を毎回再構築していた。
- `isInfoMode` 時の軍勢情報では、兵数・兵糧などが不変でも両軍のHTMLを毎回代入し、タブ一式のDOMとイベントハンドラを毎回作り直していた。
- 攻守タブの描画コードがほぼ二重に存在していたため、表示順をパラメータ化して統合できる構造だった。

## 3. 改修内容
- 移動範囲描画中だけ味方占有位置の `Set` を構築。既存の通過可能判定は保持し、敵距離・敵配列・スキル判定用味方配列は占有HEXを初めて確認した時に一度だけ求める。地形・目標距離・ZOC・隣接判定・AP・関係式の順序はそのまま。
- `updateStatus()` 内の両軍HTMLは、同一のDOM要素・同一HTMLなら再代入しない。タブは軍勢の存否・選択タブが変化した場合のみ作成する。攻守それぞれのタブ描画は単一処理に統合し、攻撃側の左からの順と守備側の逆順を維持した。
- 新しい描画同一性キャッシュはインスタンスの1か所で管理し、`initUI()` と `releaseFieldWarVisualResources()` で破棄する。前の野戦の内容を次の野戦へ引き継がない。
- 旧ループおよび重複タブ描画は撤去し、重ね書きする救済処理は追加しない。

## 4. 新旧比較・検証
- 独立した r895・r896 の実際の `updateMap()` を、部隊数2～36、移動候補15～234HEX、複数兵科・地形・海域を含む240条件とプレビュー60条件で実行し、4種のHEXハイライトの出力が**全件一致**。
- Node.js合成ベンチマーク（移動範囲480回更新、測定6回の中央値、**実機FPSではない**）：2部隊 **75.03ms→70.13ms**、8部隊 **81.83ms→72.63ms**、20部隊 **112.95ms→89.00ms**、36部隊 **182.60ms→120.57ms**。時間・使用機種で変動する。
- Chromium実ブラウザで、軍勢情報の初回・無変更再更新・攻撃側タブ選択・兵数変更・援軍消失の各状態で r895 と r896 のHTMLを比較し**全件一致**。無変更再更新のDOM変更は9件→0件。タブと軍勢表示の実DOMノードを保持すること、値の変化では更新されることを確認。
- Chromium実ブラウザの軍勢情報500回更新（測定6回の中央値）は **44.6ms→2.7ms**。これは情報パネル単体の測定で、野戦全体のFPS向上率とは異なる。
- 回帰テスト2件を追加。味方占有マスの距離再計算抑止、スキル配列の順序、ハイライト、情報タブ・兵数変化・軍勢消失時の再描画と初期化を確認。
- ロジック **1,447件成功・0件失敗・1件スキップ**。PC・スマホ・低メモリスマホの画面回帰を通過。正式マニュアル原文保護、管理Excel・BINと主要数式、近似シミュレーション4件も通過。

## 5. 継続事項
- 長時間連戦・実機低性能スマホの入力遅延とスクロールFPSについては未測定。
- 本変更はDOM更新と移動ハイライトの内部作業量に限定。その他の野戦表示ホットパスを継続監査する場合も、画面・計算・乱数・タイミングの完全一致が前提。
