## 2. 監査範囲
- `js/ui.js` の通常会話→選択肢、`closeBeforeAction`、`beginModalHandoff()` と解放条件。
- `js/war_preparation_controller.js` の出陣確認・援軍なし・他勢力援軍辞退の実経路。
- `js/war_effort.js` の非同期 `startWar()` と `before_war` 待機、開始カットインへの接続。
- 既存のロジック・画面回帰、管理Excel・BIN、正式マニュアル。

## 3. 新規発見と改修
**出陣確認後、次画面の準備中に共通暗幕を解放する可能性（重要度：中）**
- 到達経路：プレイヤーが援軍候補のない拠点から出陣する際の［出陣する］、または他勢力への援軍要請を［要請しない］としたとき。
- 原因：`startWar()` は `before_war` イベント等を `await` するPromiseを返すが、`WarPreparationController` の確認コールバックがそのPromiseを返していない。特に `async () => { proceedToAlly(...); }` は内部呼び出しが終了する前に解決する。`UIManager` の `closeBeforeOk` / `closeBeforeCancel` により旧会話が先に閉じるため、共通暗幕の引継ぎ期間が本来の画面準備より短くなる。
- 改修：`proceedToAlly()` の援軍候補なし分岐は `startWar()` を返す。最終確認のコールバックは内部処理をそのまま返す。援軍辞退コールバックも `startWar()` を返す。共通暗幕の正本は引き続き `UIManager`。固定待機時間の増設、二重暗幕、余分なラッパーは作らない。
- 維持：開始処理・援軍判断・ターン進行・BGM・SE・戦闘計算・画面の配置・ボタン文言・セーブ形式・マスター値を変更しない。

## 4. 採否・継続事項
- 他の同期コールバックで、既に次のモーダルを同一処理内で開いているものは変更不要と判断した。
- `startWar()` のPromiseを返すことで開幕演出の開始まで暗幕を保持できるが、実機の非常に遅い `before_war`、カットイン中の合成濃度、長時間連戦の聴感と描画負荷は未測定。問題が確認された場合も画面ごとの固定遅延追加を避け、既存の公開・引継ぎ契約を再検証する。
- 本監査は画面交代の経路が全て網羅されたことを意味しない。疑わしい経路は通常の操作から到達することを確認してから改修する。

## 6. 改善提案
開始前イベントを伴うコマンドは、同期モーダル確認後に非同期処理へ進む場合、画面生成を担うPromiseを共通UIへ渡す。既存UIの引継ぎを増設するのではなく、呼出元で失われた戻り値を確認する。
