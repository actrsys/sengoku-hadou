# A-117 滅亡時残党諸勢力化の城主更新保留継承（r791）

## 基準と到達性

r790完全版を基準とし、合戦で最後の拠点を失った旧家の家臣が、`LifeSystem.checkClanExtinction('no_castle')` → `AffiliationSystem.becomeRonin()` を経由して生存スキルの残党諸勢力を結成し、同じ旧家の家臣が合流する通常プレイの経路を確認した。滅亡時の各人の処遇では城主・派閥・画面を最後に確定する設計だが、残党結成と合流の内部移動が `deferCastleLordUpdate` を受け継いでいなかった。

## 修正前の再現

旧家の最終拠点が攻略家の所有になった後、そこに残る旧家家臣3名のうち1名が生存スキルで諸勢力を結成し、ほか2名が合流するfixtureを、正規の `LifeSystem` と `AffiliationSystem` の両方に接続して検証。r790の既存1,287テストは全件成功する一方、追加A-117は **1件失敗**。拠点の城主更新は一括処理の最後の1回だけでよいのに、内側の `leaveCastle()` / `enterCastle()` / `moveCastle()` を合わせて計7回呼ばれた。仮任命の可能性がある重複更新を検出したものであり、毎回必ず任命履歴が重複したと断定するものではない。

## 最小改修

- 新規残党諸勢力結成の退城・入城に `options` を渡し、城主更新保留を維持する。
- 既存残党への合流・新規結成直後の浪人回収にも同じ `options` を伝播し、`moveCastle()` の共通窓口をそのまま使用する。
- 単独の浪人化・残党合流では既定の即時更新を維持する。生存スキルの条件・兵力・忠誠度・派閥選出法・実家・セーブ形式は変更しない。
- `AffiliationSystem` の既存オプションを通すだけで、派閥・城主の独自計算や新しい処理責務を設けない。

## 検証と限界

- 修正前: **1,287成功・1失敗**（A-117は城主更新7回）。
- 修正後: **1,288成功・0失敗**（A-117は最終確定1回、3名の残党加入・派閥1回・地図描画1回）。生存者を先頭に処理する順序と、先に浪人化した家臣を後の生存者が回収する順序の両方で確認。
- `tools/verify_release_sources.js` および `tools/verify_excel_bin_parity.py` は共通・1560・1570データで合格。`tools/check_manual.py` 合格。`tools/simulation/test_player_focus_sim.py` は4件成功。`node tests/run_visual_tests.js` のPC・スマホ画面回帰は合格。
- 全乱数の長期自然観戦や全拠点の捕虜／生存スキル組み合わせの網羅試験は未実施。
