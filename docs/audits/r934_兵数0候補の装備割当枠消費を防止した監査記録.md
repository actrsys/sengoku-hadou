# r934 自動兵力配分で兵数0候補が装備枠を奪う問題の解消

- **入力正本**：ChatGPTライブラリ `sengoku-hadou-main-r933-dialog-force-reset-release-complete.zip`（完全版、内部版r933）。r927の更新済み共通データを維持。
- **監査の起点**：戦国覇道の定期コード監査の継続事項「手動兵力配分の兵数0」。定期監査自体には変更・修正を反映しない。本改修は別途ユーザーから継続制作を指示された本体作業として行った。
- **設計根拠**：`ARCHITECTURE.md` §1・§2・§6、`docs/manual/TECHNICAL_REFERENCE.md` の `TroopAllocationService` 仕様、`docs/manual/MAINTENANCE_POLICY.md`。配分計算は専門Serviceが唯一の正本。人工的な境界だけではなく、実ゲームの選択・配分・野戦生成の経路を追って判断する。

## 実到達条件と原因

- `UIInfoManager` の出陣・迎撃等の武将選択は最大5名で、選択人数を兵士数で制限していない。数量画面は1人以上の兵数指定を許すため、例えば武将5名・総兵数5人などに到達する。
- `WarManager.autoDivideSoldiers()` は `TroopAllocationService.autoDivideSoldiers()` へ委譲。総兵数が少ないと整数丸めにより、総大将以外が `req=0` になる。
- 旧実装は `req=0` も兵科装備の候補に含め、`availableGuns >= 0` が真になるので兵士0人を鉄砲部隊と判定し、`teppoCount` の部隊枠だけを消費していた。実際には0人部隊は `FieldWar` で生成されない。
- **再現例**：総兵数5・武将5・軍馬0・鉄砲5、先頭の総大将より後続武将の能力値が高く、後続武将の砲術適性が高い場合。旧版では兵士0人が先に鉄砲枠2つを消費し、兵士5人を持つ総大将は足軽になる。
- **重要度**：中。戦争時の装備配分が変化する。総兵数・勝敗処理・シナリオデータの破壊は確認していない。

## 変更と設計適合性

- `js/troop_allocation.js` の既存装備割当ループ内で `requested <= 0` の候補をスキップし、0人による装備部隊枠消費を防ぐ。
- 兵数0のエントリーがある場合でも既存の配分計算・0人部隊除外・残兵数の補充処理は維持。装備の割当規則、武将選択上限、兵科適性の計算式、UI・CSS・セーブ形式に変更はない。
- 計算責務を `TroopAllocationService` 以外に複製していない。新しい状態、互換層、タイマー、監視器、後勝ちCSSは追加しない。
- 武将数より兵数が少ない手動編成で、0人の初期値と入力 `min=1` が一致しない件は、部隊の参加可否・武将選択の仕様判断を伴う別課題として今回未変更。実画面の操作検証を継続する。

## 検証

- **修正前回帰**：追加した正本Service試験が失敗。1,495成功・1失敗・1スキップ（5人中4名が0人なのに鉄砲枠を消費し、実兵力を持つ総大将が足軽になる）。
- **修正後回帰**：1,496成功・0失敗・1スキップ。AIとプレイヤー双方で総大将に鉄砲を配分、0人候補の装備属性なし、総兵数5を維持。
- **追加スイープ**：武将1～5名・兵数1～65・軍馬/鉄砲各5段階・AI/手動2種、計16,250条件。修正前後一致15,555件、装備割当の相違695件。修正後は全条件で兵数保存・部隊上限・総大将兵数の不変条件が正常。画面のユーザー操作を全16,250件実行した検査ではない。
- `node tests/run_visual_tests.js`：PC/スマホの既存画面回帰すべてPASS。
- `python tools/check_manual.py`：PASS。
- `python tools/verify_excel_bin_parity.py`：共通・1560・1570すべてPASS。
- `node tools/verify_release_sources.js`：主要数式64,644件PASS。
- `python tools/simulation/test_player_focus_sim.py`：4件PASS。
- **検証限界**：実機の長期間の低兵力戦争、全装備配分パターンでの勝敗統計比較、手動0人行の操作経路は未実施。
