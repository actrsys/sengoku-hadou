# r834 月初「前」史実イベントと定例全国派閥再編の二重実行解消

## 到達性・再現

r833 の正本と `TurnManager` の実際の月初順序を照合した。月初は `EventManager.processEvents('startMonth_before')` → `LifeSystem.processStartMonth()`（元服）→ `FactionSystem.processStartMonth()`（下野と全国再編）という固定順で実行される。一方、r833の `EventManager` は同段階の史実イベントが正常終了すると `EventAction.refreshScreen({refreshFactions:true})` を呼び、定例再編より前に全国再編していた。史実イベントが成立する月には、所属や功績を変更しなくても全国再編が2回になる。

実 `EventManager`・`EventAction`・`FactionSystem` を使用して、`startMonth_before` の史実イベントと直後の `FactionSystem.processStartMonth()` を実行する新規回帰を作成。修正前は `updateFactions()` が2回呼ばれ、新規テストが `2 !== 1` で失敗した。前回の派閥主補正によって結果が変わり得るため、重複を無害とは扱わない。ただしこの検証は対象に絞った実装テストで、自然観戦ではない。

## 修正

- イベント終了時の威信・地図更新は従来どおり行う。
- `startMonth_before` で `FactionSystem.processStartMonth()` が後続する構造のときは、史実イベント等で再編が必要でも、そのタイミングでの全国派閥再編を保留する。元服・下野確定後に定例 `processStartMonth()` が全国一度だけ再編する。
- 単独呼出しなど定例再編の保証がない場合と、`startMonth_after`・月末・戦闘などは従来どおりイベント終了時に再編する。
- 派閥選出式、前回派閥主補正、史実イベントの成立・効果、現行の人事共通APIは一切変更しない。
- 今回の修正は `EventManager` の再編タイミングの判断であり、各イベント・所属Systemへの新たな派閥計算ロジックは増やさない。

## 回帰と限界

`tests/run_tests.js` へ「月初前イベント→定例再編で1回」「月初前の単独イベントでは即時1回を維持」「月初後イベントは即時1回」の3件を追加。修正前に追加テストは `2 !== 1` で失敗し、修正後は全新規テストが成功した。

- `node tests/run_tests.js`：**1,358件成功・1件失敗**。唯一の失敗は意図的に本体ZIPから除外されているフォントファイルの存在確認であり、今回の変更には関係しない。
- `python tools/check_manual.py`：現行規則ID、参照先、旧原文2,283行の保全が合格。
- `python tools/verify_excel_bin_parity.py`：共通・1560・1570管理ExcelとBINの一致、主要数式64,644件が合格。
- `node tools/verify_release_sources.js`：配布tree検査が合格。
- `python -m unittest -v tools/simulation/test_player_focus_sim.py`：4件成功。
- `node tests/run_visual_tests.js`：PC・スマホ・低メモリを含む既存画面回帰が合格。

実ブラウザの長期自然観戦は未実施。自動回帰の成功と自然観戦を混同しない。
