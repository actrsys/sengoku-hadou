# A-101 捕縛旧城主の解放と帰還先の城主役職整合（r775）

## 到達性と原因

城主の独立・寝返り時、旧家臣は派閥と義理によって追随・逃亡・捕縛のいずれかになる。城主としての表示状態を持つ旧家臣も捕縛対象となる。旧主家が別拠点を保持し、解放が選択された場合、`IndependenceSystem.handleCaptives()` は `setCastleIdRaw()` と `samuraiIds.push()` で帰還先を手動更新していた。

この経路は `AffiliationSystem.moveCastle()` が担う `isCastellan` の解除を実行しない。よって旧拠点の城主資格を持つ解放武将が帰還先でも `isCastellan=true` のままとなり、既に城主がいる拠点の候補選出に誤って介入し得る。元の `castellanId` のみを清掃しても、派生フラグの不整合は残る。

## 修正前の再現

旧家拠点を奪われた城主が捕縛され、旧主家の別拠点へ解放される通常の処遇経路を `resolveSubordinates()` → `handleCaptives()` で実行した。本体の `AffiliationSystem` を使い、帰還先に現任城主が存在し、捕縛された旧城主の能力が上回る配置とした。既存1,262件は成功、追加1件は `isCastellan=true` が残って失敗した。

## 修正

処遇条件・死亡処理・逃亡先の乱数抽選は変更しない。解放の3分岐に重複していた帰還処理を `releaseCaptive()` に集約。旧主家所属の保持を正規APIで確定した後、`AffiliationSystem.moveCastle(p, target.id, {stayHistoryFromCastleId: 0})` を使用する。城主役職の解除、帰還先の在城名簿更新、城主更新、派閥の着任履歴は既存正本に委譲する。帰還先がない場合の浪人化も従来と同じ `becomeRonin()` とする。新しい状態管理や履歴フィルタは設けない。

## 検査

`tests/run_tests.js` に旧城主の解放を実処遇経路から再現する回帰を追加した。r630 の捕虜帰還年月テストのモックは、これまで迂回していた正規APIが要求する `LifeStatusRules` と現任大名問い合わせを追加した。これらは本番ではすでに存在する依存であり、ゲーム本体への防御分岐は追加していない。通常の独立・寝返り、死亡時、所属変更の既存回帰を維持する。

実ブラウザで独立が発生するまでの長期自然観戦、および全捕縛分岐の網羅確認は別途未実施。
