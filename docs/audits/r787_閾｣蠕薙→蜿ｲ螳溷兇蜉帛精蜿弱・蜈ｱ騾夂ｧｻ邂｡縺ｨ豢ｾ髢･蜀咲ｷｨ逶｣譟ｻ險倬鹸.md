# A-112 臣従・史実イベントの一括勢力吸収処理の共通化（r787）

## 基準・到達可能な経路

r786を基準に、プレイヤーの外交コマンド `DiplomacyManager.executeVassalage()`、月初のAI同士／AIからプレイヤーへの臣従申し出 `common_events.js`、史実イベントの `EventAction.absorbClan()` を追跡した。いずれも領地・軍団・所属・未婚姫を扱う同型の移管処理を別々に持っていた。月初・外交の移籍は `transferClanRaw()` を利用するが、完了後に `FactionSystem.updateFactions()` を呼ばなかった。史実イベントの固定忠誠以外の経路も同様に派閥再編を行わず、固定忠誠時は `joinClan()` を武将ごとに呼んで途中再編していた。

## 修正前の再現

`AffiliationSystem`・`EventAction.absorbClan()` を読み込んだ追加結合テストで、旧家3名を新家へ吸収した場合、全員の所属は更新されるのに派閥再編の呼び出しが **0回** であることを検証した。r786の全1,279テストは成功し、追加A-112テストだけが失敗（1,279成功・1失敗）。これは即時の派閥状態更新が翌月まで遅れる、実イベント到達可能な経路である。

## 対処

- `AffiliationSystem.absorbClan(subordinateClanId, dominantClanId, options)` を一括移管の唯一の実装とする。軍団の正規解散、`CastleManager.changeOwner`、`transferClanRaw` または固定忠誠時の `joinClan`、未婚姫の既存移管窓口を使い、同一計算を増設しない。
- 史実イベント固有の「対象人物を除く」「死亡者を除く」「忠誠固定」「消滅通知」を既存の挙動のままオプションで引き渡す。イベント条件・会話は各イベントが担当し、通常外交と月初の臣従は従来の通知や操作勢力の切替を維持する。
- 最終名簿が確定してから旧家／新家の `FactionSystem.updateFactions()` を各一度呼ぶ。固定忠誠の複数 `joinClan()` 中だけ派閥・城主の途中確定とUI描画を保留し、最後に城主を確定する。
- 旧マニュアルやテストにあった「別ファイルの同じ一括処理」を期待する静的検査は、現行の共通窓口が正本となる検査へ更新する。ゲームバランス、年次データ、セーブ形式は変更しない。
