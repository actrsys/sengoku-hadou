# r830 派閥処理の共通化・一元化監査

## 問題意識と監査範囲

r829を基準に、過去のr780–r787、r790、r802、r829の派閥関連監査記録、現行マニュアルの「一意味一owner」「途中更新の保留・最終状態での確定」を参照し、`js/faction_system.js`、`js/affiliation_system.js`、`js/life_system.js`、`js/independence_system.js`、`js/diplomacy.js`、`js/event/historical_event.js`、`js/event_manager.js` と呼び出し側を横断確認した。

## 正本の分担（現行）

- **形成・選出・解散のアルゴリズム**は `FactionSystem.updateFactions(targetClanId)` が唯一の正本。選出ロジックの複製は確認されなかった。読み取り側のAI・謀反・人事の派閥参照は別の選出実装ではない。
- **所属変更に伴う旧派閥の破棄**は `AffiliationSystem.resetFactionData()` を正本とし、`transferClanRaw()`、`joinClan()`、`becomeRonin()` 等の所属変更窓口から利用する。`setClanIdRaw()` は索引更新を担う低レベル窓口で、所属移籍の完結処理ではない。r829の断交人質の修正は、この使い分けに沿う。
- **一括処遇中の再編保留と、完了時の確定**はイベントの進行責任者が管理する。原則 `deferFactionUpdate` を下位の正規APIへ渡し、全員の移籍・死亡・家督継承・所属確定後に更新する。通常の単発命令では即時更新を維持する。
- `IndependenceSystem` の限定的な仮派閥IDは謀反の一時的な勢力判定用で、`finally` で復元される。恒久的な派閥選出の第二実装ではない。ただし一時書き込みには今後も退避・復元の監査が必要。

## 実行経路で確認した重複と修正

**確認済み**: r787で `AffiliationSystem.absorbClan()` へ臣従と史実吸収を集約したとき、吸収終端で旧家・新家の `updateFactions()` を各1回実行する仕様になった。しかし、史実イベントの `EventAction.absorbClan()` 呼出元では、イベント処理完了後の `EventManager.processEvents()` が `EventAction.refreshScreen()` を呼び、改めて全国の `updateFactions()` を1回実行する。同じ史実イベントで、途中2回と最後1回の再編が重複する。

**改修**: `AffiliationSystem.absorbClan()` に既存の一括処遇指定と同型の `{deferFactionUpdate=false}` を設け、史実イベントの共通呼出元からだけ `true` を指定。通常臣従とAI月初臣従は指定しないため、以前の終端2勢力更新を維持する。史実イベントではイベント終了時の全国再編1回のみ。形成・選挙・解散の計算式、抽選条件、忠誠、姫移籍、城主任命、勢力滅亡通知、画面描画の責務は変更しない。

**再現**: `AffiliationSystem`、`EventAction.absorbClan()`、`EventAction.refreshScreen()` の実処理をロードした限定テストで、修正前は史実イベントの吸収直後に旧家・新家の更新2回、終了時の全国再編1回（計3回）だった。修正後は吸収時0回・共通終了時1回。r830のA-112回帰は史実イベントの吸収直後と終了後を別々に確認し、固定忠誠経路で途中更新を行わないことも確認する。

## 留保と確認範囲

- 一括処理の親がどのタイミングで再編するかという**スケジューリングは各専門Systemの責務として残る**。これを一つの巨大な派閥専用イベント管理器へ移すことは、一意味一ownerの改善と同義ではない。
- 断交人質から捕虜へ進む分岐等では、末端の通常捕虜処遇が個別の派閥更新を発生させ、その後に外交側の関係勢力更新も行う可能性がある。現状、失効・中断時の整合性を維持するため即時更新を必要とする分岐もあり、一律遅延の安全性は未検証。今回の修正対象から除外する。**「ゲーム全体で常にちょうど一回再編する」とは主張しない。**
- 長期自然観戦・すべての乱数列・ゲーム開始時の全史実イベントは実施していない。限定再現と既存回帰に基づく監査であり、未検証は成功扱いしない。
