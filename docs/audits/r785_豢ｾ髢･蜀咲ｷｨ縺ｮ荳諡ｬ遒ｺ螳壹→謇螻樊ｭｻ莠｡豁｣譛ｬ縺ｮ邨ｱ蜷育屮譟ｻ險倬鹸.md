# A-110 派閥再編の呼出し一元化・一括処理の中間再編排除（r785）

## 監査対象と結論

r784 を基準に `FactionSystem`、`AffiliationSystem`、`LifeSystem`、`IndependenceSystem` をまたぐ派閥形成・解散と所属・生死の変更経路を監査した。**派閥選出アルゴリズム自体は `FactionSystem.updateFactions()` に一元化されている**。`IndependenceSystem` に別個の派閥選挙アルゴリズムはなく、所属変更は `AffiliationSystem` の正本、処断は `LifeSystem.executeDeath()` を用いる。ただし、イベントや月初で一括変更する途中に、下位の正規処理が *都度* 派閥再編してしまう経路を発見した。これは同じ判断を個別に実装する問題ではなく、**呼出しタイミングの重複・先走り**である。

## 実際に到達する経路

1. 月初 `FactionSystem.processStartMonth()` → 下野候補を順に `executeRonin()` → `AffiliationSystem.becomeRonin()` が各人の旧主家を再編、最後に `processStartMonth()` 自身が全国を再編。下野2名の実クラス結合試験で **3回の再編**を確認。月初に下野者全員を決めてから再編するのが既存の仕様であり、途中選出は不要。
2. 独立・寝返りで捕縛され、AI判断で処断される武将を `IndependenceSystem.handleCaptives()` から `LifeSystem.executeDeath()` に渡す際、通常の死亡後再編が各捕虜で発生する。2名の処断を模した実メソッド＋死亡窓口契約の結合試験で **2回の途中再編**を確認。独立・謀反の最終派閥更新は r780～r784 の各戦後確定地点ですでに行われる。
3. 旧家に残る拠点がなく反対派が浪人になる場合も、個人の `becomeRonin()` が途中再編を行う余地があった。さらに滅亡後の生存スキルによる残党諸勢力化では、既存の `deferFactionUpdate` と `deferUI` を通常の浪人化と異なり無視していた。特別な生存・合流の挙動は維持する。

## 最小改修と責務

- 月初下野は `becomeRonin(..., { deferFactionUpdate: true })` を使い、`processStartMonth()` 最後の既存の全国 `updateFactions()` を唯一の再編地点とする。
- 独立中の捕虜死亡では `LifeSystem.executeDeath(p, { deferFactionUpdate: true })` を使う。捕虜の死亡確定・姫/人質/官位/名簿整理は従来どおり LifeSystem が実施する。反対派の下野・帰還先なしの浪人化も `AffiliationSystem.becomeRonin()` で中間再編だけ保留する。
- `AffiliationSystem.becomeRonin()` が残党の新規諸勢力化・既存残党合流に入る場合も、同じ更新保留引数を伝播させる。単発の通常処理は引数の既定値により従来どおり即時更新・描画する。
- 派閥計算を別クラスへ複製せず、独立側へ新たな候補選出・中間状態の補完は追加しない。既存の謀反勝利の一時功績補正、引き分けの一時派閥復旧、独立後の旧主家一度だけ再編を維持する。

## 検証と限界

- 修正前 r784 に新規の4契約テストを接続した結果 **1,273 passed / 4 failed**。月初二重以上の再編、捕虜処断の途中再編、残党結成・合流での保留無視が実際のコード経路に沿って再現された。
- 修正後 r785 の同じセットでは **1,277 passed / 0 failed**。r780～r784 の謀反三分岐・通常独立回帰も継続成功。追加テストは本番クラスと一部契約スタブによる結合・単位検証であり、長期自然観戦による全乱数分岐の実測ではない。
- `tools/check_manual.py`、`tools/verify_release_sources.js`、`tools/simulation/test_player_focus_sim.py`、`tests/run_visual_tests.js` を出荷時に再実行する。管理Excel/BIN、画像、フォント、外交関係、セーブスキーマ、確率・能力調整値の改変なし。
