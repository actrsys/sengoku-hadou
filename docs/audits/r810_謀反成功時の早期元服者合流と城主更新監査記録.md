# A-138 謀反成功時の早期元服者合流と城主最終確定（r810）

## 対象と実ゲームでの到達性

`IndependenceSystem.planCoupDetatOrRebellion()` の謀反成功 (`coup` → `rebel_win`) 分岐。旧主家の家臣を浪人化して逃亡先へ集めたあと、同じ旧家の一門で未登場の武将が現在年までに出生済みなら、その場で早期元服して同行する。シナリオの開始年と出生年には差があるため、出生済み・未登場という状態は開始データにも存在し、特殊な壊れたセーブを必要としない。

## 修正前の再現

r809では先に旧主家の退避関係拠点を一度ずつ再選出した後、早期元服した人物を `AffiliationSystem.enterCastle()` の即時更新で追加していた。既存のr779結合テスト（謀反成功・旧当主追放・有効な旧家一門・友好家の逃亡先）を拡張し、退避先の `updateCastleLord()` 呼出回数を測定すると、早期元服者1人の入城で **2回**（本体の最終選出1回＋入城時1回）となった。後者は他家城へ浪人として入城するため通常は追加任命履歴を生まず、今回の観測範囲では結果の誤りより同一命令内の重複選考が問題だった。城主変更履歴が必ず発生するとは主張しない。

## 最小改修と責務

- 敗残武将の所属変更と位置・在城名簿・早期元服者の入城は従来どおり `AffiliationSystem` が担当する。早期元服者の `enterCastle` には `deferCastleLordUpdate` を渡して途中の選考だけを止める。
- `IndependenceSystem` は旧主家敗残者の処遇条件と影響拠点集合を管理し、**通常の敗残者と早期元服した一門をすべて配置した後**、既存の `game.updateCastleLord()` を通じて各拠点を一度だけ確定する。
- 勝敗判定、退避先の選択、早期元服の条件・所属先、外交関係・派閥再編、ゲームバランス・管理Excel・セーブ形式は変更しない。独立Systemに城主の選考や在城名簿操作の重複実装を増やさない。

## 検証結果と限界

- 修正前 r809本体＋追加断言：従来の1,324件のうち拡張したr779の1件だけ失敗（退避先城主更新2回、期待1回）。
- 修正後：同じテストで更新1回となり、元々の早期元服・他家所属予定者・未出生一門の保護条件もすべて成功。ロジック合計 **1,324件成功・失敗0件**。
- これは製品 `IndependenceSystem` と `AffiliationSystem` を組み合わせ、発生可能な謀反勝利結果を固定した結合検証。自然観戦を通じた全乱数・全シナリオの網羅検証ではない。
- 配布物はフォントを含めず `data/fonts/` の空フォルダのみ残す。検証環境にフォントを一時配置した場合と、配布ZIPの収録内容を区別する。
