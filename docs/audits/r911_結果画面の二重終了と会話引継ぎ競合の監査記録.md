# r911 結果画面の二重終了と会話引継ぎ競合の監査記録

## 1. 監査対象・正本
- 正本：ChatGPTライブラリの完全版 `sengoku-hadou-main-r910-dialog-choice-backdrop-click-fix-utf8-complete.zip`（内部版 r910）。
- 範囲：`UIManager.showResultModal()` / `closeResultModal()`、断交後の人質・姫処遇へ続く結果画面の引継ぎ、連続押下、通常閉鎖、強制終了、PC・スマホでの表示。
- 根拠：`ARCHITECTURE.md` の実ゲーム到達性、重複イベント禁止、共通UIへの責務集約、会話handoff、固定msでなく実際の表示完了を待つ契約。

## 2. 新規発見：高（実コードの二重操作で再現）
- `handoffToNextDialog` を指定した結果画面では、次の会話を用意するまで前の結果画面を可視のまま維持する。
- r910は1回目の `closeResultModal()` で `onResultModalClose` と `resultFollowupDialogHandoff` を消費するが、結果画面は可視のまま残る。利用者が閉じるボタンを再度操作すると、2回目が **通常終了**として再入し、背景復旧・`game.checkAllActionsDone()` が走り、結果画面を次の会話より先に閉じてしまう。
- 新規ロジック回帰テストは修正前のr910で `2回目の押下で旧結果画面を先に消さない` に失敗した（1,469件成功・1件失敗・1件スキップ）。
- 会話遷移以外の結果画面でも、閉鎖の描画待機中に再度押すと終了を重ねて呼ぶ構造だった。

## 3. 原因・改修方針
- 表示状態（`hidden`かどうか）は画面の終了途中も変わらない。表示と終了受付の状態を混同していたことが原因。
- `js/ui.js` に結果画面の終了受付状態 `_resultModalClosing` を一つだけ持たせ、初回の閉じ操作で受付終了、実際の閉鎖完了後に解除する。
- 新しい結果画面が表示された場合、または `forceResetModals()` による画面全失効では受付状態をリセットする。
- 既存の `beginVisualHandoff()`、`closeCoveredViewAfterRecovery()`、`prepareCoveredViewForOpen()` は正本として維持する。旧クリック監視の復活、個別暗幕・タイマー・別のイベントシステム追加は行わない。
- 戦後処遇・外交判定・会話テキスト・レイアウト・SEは変更しない。
