# A-094 城主任命の連続履歴と複数武将移動の最終確定（r768）

## 事実・到達経路

- `HistorySystem.record()` 自体の二重追加ではなく、`AffiliationSystem.electCastellan()` が実際に別の城主IDを選ぶたび正規の任命履歴を記録していた。
- 敗戦後の `WarManager.processCaptures()` は旧城主を含めて城内武将を1名ずつ捕縛・退避していた。各人の `leaveCastle()` / `moveCastle()` が即座に `updateCastleLord()` を呼ぶため、退避途中で残留していた人物を仮の城主として何度も任命できた。通常の戦争処理で到達する。
- 1560年の石川城（城ID190、所属家ID68）の開始データを用い、旧城主を含む複数武将の敗戦退避を通常の `processCaptures()` から再現した。r767では退避途中の城主任命履歴が残り追加回帰が失敗した。

## 改修

- `AffiliationSystem.moveCastleGroup()` を、一命令で複数武将を移動する正規窓口として設置。各人の `moveCastle()` の在城・軍団処理を維持し、出発元・到着先の城主は全員の移動後一度だけ決める。AI複数配置、AI居城移転、プレイヤーの一括移動を接続する。
- 攻城戦の捕縛・敗走では、捕虜と退避者を一人ずつ処遇してもその途中の城主再選出だけを保留する。退避先は処理完了後に更新し、陥落元は占領処理で最終確定する。撤退先選定・捕縛確率・軍団処理・人員の所属・在城履歴は既存正本を使用。
- `HistorySystem` に一律の重複削除を追加しない。異なる命令で本当に任命が変わったときの履歴はそのまま残す。

## 検証

- 修正前：既存1254件成功、追加1件失敗（石川城で敗戦退避中の仮城主履歴）。
- 修正後：一括退避と一括移動の追加2件を含めて1256件成功、失敗0件。
- マニュアルの城主・所属・履歴の責務分担を維持し、AIの選定得点・捕縛確率は変更しない。

## 注意点

同じ月に独立した別の人事命令・落城によって実際に城主が変わる場合の履歴は抑止しない。長期自然観戦での全分岐頻度は未測定。
