# r907 援軍通知から開戦への非同期引き渡し監査記録

## 1. 監査対象
- 正本：ChatGPTライブラリのr906完全版 `sengoku-hadou-main-r906-gunshi-advice-promise-handoff-utf8-complete.zip`（内部版r906）。
- 監査範囲：`WarPreparationController` → `WarManager.reinfMsgHelper.showRefusal/showAcceptance/showRequest` → `UIManager.showDialog()` → `WarManager.startWar()`。通常の援軍なし開戦と、諸勢力・大名家援軍、プレイヤーからの援軍辞退、手動派遣を比較。
- 規範：`ARCHITECTURE.md`、`docs/manual/TECHNICAL_REFERENCE.md`、`docs/manual/MAINTENANCE_POLICY.md` のUI・非同期画面遷移・戦争の担当区分。

## 2. 新規発見（重要度：中）
- 援軍拒否・承諾の通知後に開戦するコールバックで、`startWar()` のPromiseを返していなかった。実際の `executeReinforcementRequest()` にモックした非同期 `startWar()` を通すと、大名家側の拒否・承諾の双方で通知の確定コールバックが `undefined` を返した。
- `startWar()` は `before_war` イベントと戦場の準備を待つ非同期関数である。通知が `closeBeforeOk` で先に閉じても、UIにPromiseが伝わらなければ、その画面の共通暗幕保持が開戦準備に連動しない。
- 手動援軍の「出発しました」通知は、従来 `closeBeforeOk` の指定がなく、画面遷移先が会話ではなく戦場であることを共通UIへ伝えていなかった。

## 3. 改修・採否
- 諸勢力の承諾／拒否、大名家の承諾／拒否、プレイヤーからの援軍辞退後の通知、手動援軍出発通知で、既存の `startWar()` の戻り値をそのままUIへ返す。
- 手動援軍の出発通知は `closeBeforeOk: true` を指定し、ほかの開戦通知と同じ「別画面への遷移」として扱う。表示内容・確認ボタン・演出時間は変更しない。
- 影響範囲外のAI自動開戦や援軍募集・派遣の判断、資源消費、兵力配分、戦闘ルールは維持する。UIManagerへのタイマー・ラッパー・ガード・新規フラグ追加は不要と判断し不採用。

## 4. 検証結果
- 修正前：本番 `WarPreparationController` の大名家拒否・承諾の開戦通知コールバックが `undefined` を返すことを再現。
- 修正後：実際の `WarPreparationController` を用いた新規回帰で、諸勢力・大名家の承諾／拒否4経路、プレイヤーからの援軍辞退、手動援軍の計6経路で、非同期 `startWar()` と**同一のPromise**が返ることを確認。
- ロジック：1,466成功、0失敗、1スキップ（配布フォント本体の意図的な未収録）。
- PC・スマホ・低メモリ表示の既存Chromium画面回帰：成功。
- 正式マニュアル検査、管理Excel・BIN出力一致、近似シミュレーション4件：成功。
- 実機での長時間連戦、各援軍イベントの実音声・すべてのフレームでの暗幕表示は未検証。今回の変更は表示引き渡し契約であり、ゲームルールやセーブ形式の変更ではない。
