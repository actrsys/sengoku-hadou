# A-118 諸勢力一括取込の城主・画面更新確定順序（r792）

## 到達性と既存正本

r791基準。プレイヤーが自家所有拠点の諸勢力を取込コマンドで説得成功する `CommandSystem` → `KunishuSystem.executeKunishuIncorporate()` → 各武将の `AffiliationSystem.joinClan()` を対象とする。城主不在は許容状態であり、所属家の武将が拠点にいても城主不在の状況は成立する。4名取込の時、派閥再編はr786で1回へ統一されていたが、`joinClan()` は城主再選出と地図描画を一人ごとに実行し、城主不在の自家拠点では最初に残っていた低実績の家臣を選んで、後から加わった有力家臣を正式選出の候補から実質的に排除し得た。

## 再現と最小修正

通常コマンドから選べる自家所有拠点に諸勢力4名と取込担当の家臣が同居し、大名は別拠点に所在・現拠点の城主が不在というfixtureを、正規 `AffiliationSystem` / `KunishuSystem` / `FactionSystem` に接続した。追加A-118はr791で失敗し、城主更新8回を計測。更新途中に担当家臣を先に城主へ選ぶことも確認。既存1,288件は合格した。

- `executeKunishuIncorporate()` から `joinClan()` に既存の `deferCastleLordUpdate: true` / `deferUI: true` を `deferFactionUpdate: true` と同じオプションとして渡す。
- 全員の取込後、既存の `GameManager.updateCastleLord()` を一度だけ呼んで最終名簿から城主を選ぶ。派閥再編は従来どおり最終名簿で1回。
- `showResultModal` の既存終了コールバックでパネル・地図を更新し、途中描画を繰り返さない。通常の単独仕官・既存城主維持・兵士合流・諸勢力友好度・外交・担当者の行動済み処理はそのまま。
- 所属変更と城主選出の計算は既存専門Systemのみ。新しい独自判定や新しいAPIは作らない。

## 検証と限界

- r791＋A-118: 1,288件成功・1件失敗。城主選出8回。
- r792: 1,289件成功・失敗0件。城主選出1回、取込完了後の地図描画1回、派閥再編1回。既存城主保持と最終名簿の有力者選出を検査。
- `r712` の取込補助テストには、既存本番API `GameManager.updateCastleLord()` のテスト側委譲を補い、仕様の判定を緩めない。
- マニュアル検査・管理Excel/BIN整合性・ブラウザ画面回帰などは別途実行したログで判定する。
