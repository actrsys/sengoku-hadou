# r795 史実イベントの複数仕官をイベント用の共通窓口へ統合

## 発見

r794では `AffiliationSystem.joinClanGroup()` が将軍庇護1・2の二つの個別実行箇所から直接呼ばれていたが、別の史実イベント「将軍就任」では従来の `followers.forEach(...joinClan...)` が残っていた。所属計算そのものは共有できても、イベント側で毎回 `deferFactionUpdate` / `deferUI` を指定する必要があり、将来の史実イベントで同じ中間更新を再発させる余地があった。

## 設計と改修

- 史実イベント共通の `EventAction.joinClanGroup(game, bushos, newClanId, newCastleId, {fixedLoyalty, keepAchievement, deferCastleLordUpdate})` を設置。イベント終了時に `EventManager` が派閥・画面を一度だけ更新する契約に従い、この窓口では両方を必ず保留する。個々の所属・功績・忠誠・婚姻・着任履歴は `AffiliationSystem.joinClan()` のままであり、選出ロジックを複製しない。
- 将軍庇護1・2の仕官をこの共通イベント窓口へ移行。発生条件と効果は変更しない。
- 将軍就任でも家臣移籍を同じ窓口へ移行。将軍候補と槇島城主の選定は元の史実イベントが行うが、正式配置が終わるまでは城主更新・地図更新を保留し、最後に影響のあった旧拠点・二条御所・槇島城を一度ずつ確定する。
- `AffiliationSystem.joinClanGroup()` は、正式任命のために城主更新を保留した場合でも、影響した拠点と勢力のID一覧を返す。対象者ゼロでは何も更新しない。通常の個別仕官、`moveCastleGroup()`、臣従による `absorbClan()`、軍団・官位・外交・各イベントの発生条件は変更しない。

## 新規史実イベントの作成契約

史実固有の人物と発生条件を決め、複数仕官なら `EventAction.joinClanGroup` を一回呼ぶ。イベント側で武将ごとに `joinClan` を回さない。特定の城主・大名の就任がある場合は城主更新を保留して配置を確定し、戻り値の `affectedCastleIds` を一度ずつ更新する。派閥・画面はイベント終了時の共通更新に委譲する。武将単独の仕官は従来の正規APIを利用する。

## 検証と限界

- 史実イベント用窓口の呼出し契約、空配列の無操作、正式城主を後から決める場合の影響拠点を実行テストで確認。
- 将軍庇護1・2の既存実条件による結合試験および将軍就任の家臣候補0人・存在時、旧拠点の退去処理を含む既存回帰を再実施。
- 今後の新しいイベントでも共通APIの使用は必要（登録だけで自動変換はしない）。長期間の全自然進行での分岐網羅は未実施。
