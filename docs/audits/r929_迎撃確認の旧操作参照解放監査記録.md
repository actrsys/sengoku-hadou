# r929 迎撃確認モーダルの旧戦争操作参照の解放

- **監査対象**：ChatGPTライブラリ `sengoku-hadou-main-r928-slider-modal-lifecycle-cleanup-complete.zip`（r928）。前回r927で取り込んだ共通ExcelとBINは維持。
- **監査範囲**：`UIManager.forceResetModals()`、野戦／籠城選択の `#intercept-confirm-modal`、`#btn-intercept`、`#btn-siege`、迎撃からの武将・数量・部隊分割選択、取消復帰、戦争確定。
- **設計根拠**：`ARCHITECTURE.md` の実ゲーム到達性、専門画面状態の正規解放、旧処理を残した上書き禁止、ゲーム計算・表示・CSS不変更、無意味な新タイマー追加禁止。

## 1. 発見した問題・到達性

**重要度：中（固定DOMに残る旧戦争データの不要な参照保持）。**

守備側プレイヤーの直轄拠点が攻撃され、迎撃可能な兵がいる場合、`war_effort.js` の `showInterceptDialog()` は固定ボタン2つの `onclick` にその戦争の攻守拠点・武将・援軍・後続callbackを閉じ込める。旧版は［籠城］や迎撃部隊の最終確定時にモーダルを隠すだけで、ボタンから旧クロージャを解放していなかった。別タブ操作権移転時の `returnToTitle()` → `forceResetModals()` も全モーダルを非表示にするだけで、同じハンドラを残していた。見えないボタンからの参照保持があり、古いスマホで不要なメモリ保持につながり得る。メモリ使用量そのものの実機計測は未実施。

ただし［迎撃］を選んで武将・数量を選択し、［戻る］で迎撃確認に戻る経路は既存仕様。そこで途中の非表示だけで `onclick` を消してはならない。

## 2. 修正方針と変更

- 固定ボタン2つの `onclick` を同時に解除する `UIManager.releaseInterceptConfirmActions()` を単一窓口として追加。
- 新しい迎撃確認を公開する前、［籠城］で最終決定した直後、迎撃部隊編成が確定した直後に同じ窓口を利用。［迎撃］を押して子選択へ進んだだけでは解除せず、取消時の再公開・再選択を維持。
- `forceResetModals()` は全モーダルを非表示にした後、同じ窓口で旧戦争参照を解放。強制終了で旧アクションを実行しない。
- **不変**：戦争結果、部隊編成・勝敗計算、UIの表示順・CSS、シナリオ・共通データ、音、画像。固定待機・監視器・二重正本を追加しない。
