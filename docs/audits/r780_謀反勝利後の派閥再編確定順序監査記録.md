# A-106 謀反勝利後の派閥再編を新当主就任後に一度だけ確定（r780）

## 実ゲームでの到達性と修正前の問題

月末の独立判定または既存の謀反イベントから `IndependenceSystem.planCoupDetatOrRebellion()` の謀反成功（`rebel_win`）へ至る。謀反勝利で旧当主と敗残家臣を複数名 `AffiliationSystem.becomeRonin()` へ送るが、従来は各人の浪人化の直後に `FactionSystem.updateFactions(oldClanId)` を走らせた。その間は新当主 `rebellionLeader.isDaimyo` がまだ `false` なので、謀反首魁が派閥主候補として選ばれ得る。後続の `resetFactionData(rebellionLeader)` が派閥主の所属・フラグだけを解除しても、追随する家臣の派閥ID／派閥名が残る。次の派閥月初更新まで、派閥主不在の所属者が存在する。

実装の `IndependenceSystem`、`AffiliationSystem`、`FactionSystem` の3クラスを結合し、二人の有力な派閥候補、四人の追随者、旧当主と忠臣という通常の家中構成から、謀反成功の有効な戦闘結果で再現した。旧版では、途中の派閥再編が2回実行され、就任後の首魁の派閥IDは0になる一方、追随者2人に派閥ID101と派閥名が残った。このテストは通常の謀反勝利結果を固定した結合テストであり、自然発生を観戦した長期E2Eではない。

## 最小改修と責務

- 既存 `becomeRonin()` の `options` に `deferFactionUpdate` を追加する。謀反勝利の複数敗残者の処理からだけ指定し、各人の通常の浪人化、所属・姫名簿・人質・在城の正規処理は維持する。
- 同じ事件の全員の逃亡、新当主フラグ、新旧勢力の統合処理が確定した後で `FactionSystem.updateFactions(oldClanId)` を一度だけ実行する。派閥主再選出は既存の `FactionSystem` に委譲し、独立Systemに独自の派閥判定を作らない。
- 通常の下野、独立、寝返り、謀反敗北、所属管理の通常呼出しは変更しない。政治能力、忠誠、確率、初期データ、セーブ構造は変更しない。

現行 `ARCHITECTURE.md` 第1・2・3・6節の「一括処理の途中状態を結果へ持ち込まない」「所属・派閥の責務分離」「実ゲーム経路での最小修正」に合致する。現行ルールの変更はないためマニュアル正本と技術リファレンスは無変更。
