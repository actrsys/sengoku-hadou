# A-135 独立・寝返り中の城主最終確定と専門責務の整理（r807）

## 対象と到達性

通常の月末独立判定 `IndependenceSystem.checkIndependence()` → `executeRebellion()` は、派閥主が別拠点の城主である場合、他の城主が呼応する場合、遠方同派閥家臣が移動する場合を順に処理する。r806ではその途中で `updateCastleLord()` が呼ばれる場所が複数あり、独立中にすでに保留対象へ追加された拠点にも重複して再選出を掛け得た。また遠方家臣だけは `moveCastleGroup()` の即時選出を使用し、処遇全体での保留を共用できなかった。元の大名家の残存拠点がなくなり、忠臣が浪人になる経路でも `becomeRonin()` に城主更新・画面更新の保留を渡していなかった。

今回の問題は実装された独立・寝返りの条件と呼び出し順序から到達可能な処理経路。再現テストでは実コードの `moveCastleGroup()` に同一一括処遇用の保留指定を渡すと途中で城主選出が走り、`resolveFactionWideRebellion()` が保留集合を受けても途中で即時選出した。浪人化については一括処理の `becomeRonin()` 呼出引数を観測して保留漏れを確認した。全条件がそろった自然な長期観戦での仮任命履歴発生までは実証していない。

## 改修と責務

- `AffiliationSystem.moveCastleGroup()` に一括処遇用の選出保留を追加。個人の所属・名簿・在城履歴の更新は従来の `moveCastle()` を通し、出発元と到着先の拠点IDだけを共通の集合へ渡す。通常のプレイヤー命令・AI一括転任・史実イベントは即時最終選出を維持。
- `IndependenceSystem.executeRebellion()` は、決起拠点、別拠点の神輿、呼応城、逃亡・捕虜解放先、遠方家臣の転出入先を同じ保留集合へまとめ、**最後に一度だけ**城主更新を依頼。城主資格の算定や任命履歴の生成は `AffiliationSystem` の正本に任せる。
- 呼応した城主と同行家臣、最後の旧家残留者が浪人になる場合も途中の選出・描画を保留。浪人の移動先が決まった後に出発元と実際の転居先を収集。通常の独立なしの単発下野は維持。
- 家督・国主継承順位、城主候補評価、派閥呼応の確率、外交関係、武将値、管理Excel、BIN、セーブ形式、画面外観には変更なし。

## 変更前後の再現

- 新規回帰3件は変更前実装では「一括転任が対象IDを返さない」「呼応城主を途中で再選出する」「浪人化に保留が伝わらない」により失敗。変更後は3件とも成功。
- 既存の独立・謀反・出奔・国主・城主・家督・外交・戦争のロジック回帰を合わせ `node tests/run_tests.js` **1,320件成功、0件失敗**。
