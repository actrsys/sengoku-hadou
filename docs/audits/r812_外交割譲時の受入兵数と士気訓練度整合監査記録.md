# A-140 外交割譲時の兵力上限と士気・訓練度の整合（r812）

## 対象と実ゲームでの到達性

`DiplomacyManager.applyCastleCessionData()` は従属・和睦の拠点割譲条件で、譲渡元に残る武将と兵・物資を譲渡元大名家の別拠点へ退避させる。退避先の兵数が上限99,999に近い状態と、割譲元に複数の兵が残る状態はいずれも通常の徴兵・輸送・戦闘で到達可能。特別な壊れたセーブを前提としない。実プレイでの発生頻度・長期自然観戦の網羅確認は未実施。

## 修正前の再現

r811の製品 `DiplomacyManager` と `AffiliationSystem` を結合し、退避先兵数99,998・割譲元兵数30,000、退避先の訓練度90・割譲元の訓練度10とした。実際に移籍した兵数は1人なのに、旧処理では30,000人すべてを加重平均へ加え、退避先の訓練度が **71** となった。受入人数1人だけを使うと **89** が正しい。新規回帰テストA-140を修正前のr811実装へ追加すると、同テストは失敗した（他にフォント未収録の単独テスト1件も失敗）。

## 原因・責務分担・修正

- `DiplomacyManager.applyCastleCessionData()` は兵数について上限で切り詰めていたが、その直前の士気・訓練度は上限超過で失われた兵まで含む合算兵数で計算していた。
- 外交Systemが既存の `GameConfig.Limits.CastleStock` から今回の実受入人数 `acceptedSoldiers` を確定し、**同じ人数**を兵数の加算と `GameMath.weightedAverageFloor()` の重みに用いる。計算式を外交Systemへ複製せず、既存の算術正本を使用する。
- 受入人数が0人なら退避先の士気・訓練度を維持する。全員収容可能な場合は従来の加重平均、受入上限99,999、資源移転、割譲元への補充兵、所属・軍団・城主選任、在城履歴、外交成立条件は変更しない。
- `AffiliationSystem.moveCastleGroup()` が武将の一括配置、`CastleManager.changeOwner()` が所有権更新、`GameMath` が加重平均という専門責務を維持する。新しい共通ラッパーや第二の兵数正本は追加しない。

## 回帰・検証

- 新規A-140結合テスト: 99,998＋30,000（1人受入）、2,000＋3,000（全員受入）、99,999＋3,000（0人受入）の3条件で兵数・士気・訓練度と割譲・転任を確認。
- フォント本体を検証環境にだけ一時配置したロジックテスト: **1,327件成功・失敗0件**。フォントなしの配布構成ではフォント存在検査1件のみ失敗し、製品動作の失敗とは区別する。
- マニュアル検査、管理Excel/BIN・主要数式、シミュレーション4件: 合格。表示回帰とZIP整合性は配布直前に別途検査する。
- 管理Excel・BIN・セーブ形式・ゲームバランスは変更していない。長期自然観戦と全乱数列の実戦検証は未実施。
