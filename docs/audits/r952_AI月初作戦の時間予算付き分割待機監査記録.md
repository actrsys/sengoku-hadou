# r952 月初AI作戦の時間予算付き分割待機 — 改修・設計・回帰監査

## 対象・到達経路

- 正本：ChatGPTライブラリの `sengoku-hadou-main-r951-ai-castle-turn-zero-delay-complete.zip`（完全版）。
- 実際の経路：`TurnManager.startMonth()` → `AIOperationManager.processMonthlyOperations()` → 生存勢力ごとの外交準備・過去所領記録・軍団別作戦更新。
- r951では生存勢力を1つ処理する直前に**毎回 `setTimeout(0)`** していた。Chromiumでは連続した短タイマーが約4ms単位に制限され、計算自体が軽い勢力でも勢力数に応じた待機が蓄積する。
- 実装済みの月初ガードは `TurnManager.startMonth()` が `waitForNextPaint()` を待ってから全国作戦処理へ入る。スマホ向けの「2軍団ごとの待機」と「作戦生成後の待機」は別に存在する。

## 改修内容と設計上の判断

- `js/ai_operation.js` の**生存勢力ごとの固定待機だけ**を、最初の生存勢力では必ず `setTimeout(0)`、以後は直近の待機から約8ms以上経過したときに待機する処理に変更。
- 時刻取得は `performance.now()`（存在しない軽量実行環境だけ `Date.now()`）を使用。閾値・待機管理は当該月初作戦呼出内のローカル変数に限定し、ゲーム状態やセーブデータへ追加しない。
- 各勢力の順序、外交判断、作戦の判定・保存、軍団別順序、乱数呼出箇所、月次履歴は不変。各勢力の処理前には引き続き `isCurrentFlow()` を確認し、`await` 後の失効判定、滅亡の再確認、軍団失効判定を維持。
- 端末負荷の高い軍団処理は従来どおり途中で制御を返す。固定待機を全廃してひと続きの同期計算にする変更ではない。
- `ARCHITECTURE.md` の責務分離・実到達性・無益な待機の削減・古いスマホでの処理分割、`docs/manual/TECHNICAL_REFERENCE.md` のAI／ターン分割契約を照合。ルール自体の変更はないのでマニュアル正本は更新しない。

## 比較・バグ的挙動検証

1. **Chromium実ブラウザで製品 `AIOperationManager` の月初メソッドを使用**。75生存勢力／各1拠点、軍団0、外交・作戦の計算を単純化した合成fixtureで新旧の処理順と作戦保存数を比較。いずれも同一（各勢力の外交→作戦→徴兵拠点選出、作戦75・履歴75・徴兵選定先75）。処理時間の中央値は、PCで軽い処理：310.3ms→約1.0ms、0.25msの人工CPU処理/勢力：330.3ms→23.3ms、1msの処理/勢力：380.6ms→116.5ms。スマホモードでは順に773.0→619.3ms、798.8→637.6ms、845.8→690.9ms。スマホの既存軍団単位待機はそのまま残る。

5. `node tests/run_visual_tests.js`：PC／スマホ／低メモリモード、会話の画面引渡し、年初・月末通知等の既存実ブラウザ検査を通過。

## 限界・継続事項

- 上記の大きな短縮値は**合成fixtureでの月初AI作戦管理処理**のみ。実際の戦争・外交・歴史イベント、ゲーム全体の月送りを含む短縮率ではない。端末・勢力数・一軍団の負荷で変動する。
- 低性能スマホ実機での長時間自然観戦、端末の熱・省電力時のフレーム変動、全史実イベントと戦争の組合せは未実施。確認した範囲で新規不具合は検出されなかったが、全環境での無欠陥を保証しない。
- 試案として調べた空の操作メニュー再消去は、実ブラウザの微小負荷では効果が小さいため採用しなかった。
