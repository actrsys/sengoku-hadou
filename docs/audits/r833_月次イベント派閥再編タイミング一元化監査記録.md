# r833 月次イベントにおける全国派閥再編の重複解消と最終確定契約

## 調査対象と実際の到達経路

r832 を基準に `TurnManager` → `FactionSystem.processStartMonth()` → `EventManager.processEvents(startMonth_after)` → `EventAction.refreshScreen()` を実コードで確認。月初下野の後に全国再編が完了したにもかかわらず、`peoples_loyalty_decrease_monthly` と `trade_income_monthly` は `checkCondition() === true` を毎月返し、`EventManager` は状態に関係なく「イベントが動いた」だけで全国派閥を再編していた。これは通常進行で毎月到達する。別途 `startMonth_before` の一揆・雪害など、`endMonth_after` の疫病・地震でも同型の余分な再編があり得る。

派閥得点には前回派閥主の残留ボーナス・移籍ペナルティがある。実際の `FactionSystem` と1560/1570シナリオの初期データから構成した局所検証では、同じ武将の所属・功績を変えずに `updateFactions()` を続けて呼ぶと派閥所属が変化する例があった（1570年の家族リンクを実 `FamilyLinker` で計算したfixtureで371人）。この数はフルゲームの初期化後の人数ではなく、検証fixtureでの変化数としてのみ扱う。したがって再編回数の重複は性能だけでなく結果にも影響し得る。現行の前回派閥主ボーナスを変更して結果だけ安定させるのではなく、不要な再編の発火源を直す。

さらに月次浪人仕官は個々の `joinClan()` が即時派閥再編し、月次AI臣従は `absorbClan()` が毎回旧家・新家を再編する一方、双方ともイベント終了時に全国再編を行う重複があった。複数人・複数勢力を同月に処遇する場合、途中段階で派閥選挙を行うことにもなる。

## 修正と責務

- `EventManager` がイベントごとの `factionRefreshMode` を読む。未指定は従来どおり再編（史実などの互換）、`none` は画面・威信のみ更新、`ifChanged` は `execute()` が `true` を返した場合だけ全国再編。複数イベントがあっても終了時に全国一度に集約。
- `EventAction.refreshScreen(game, { refreshFactions })` は全国派閥の実行有無のみを受け取る。威信・画面の更新、画面寿命検査、順序と描画の分割は従来どおり。
- 月次経済・災害等9件は `none`。月次浪人仕官・月次AI臣従は `ifChanged`。それぞれ所属変更を `joinClan(..., { deferFactionUpdate:true, deferUI:true })`／`absorbClan(..., { deferFactionUpdate:true })` に委ね、実変更があった場合だけイベント終了で全国再編。
- イベント実行中に通常例外が発生した場合、確定済み所属の派閥保留を放置しないよう共通終了処理で再編と画面更新を試みる。シナリオ／ターンの寿命が失効した通常の中断は従来どおり触らない。
- 派閥の計算、前回派閥主補正、登用・臣従確率、所属・忠誠・婚姻、経済・災害効果、セーブ形式・履歴仕様は変更しない。通常の外交コマンドの即時再編と史実イベントの全国再編は維持。

## 検証・境界

`tests/run_tests.js` に5件の回帰を追加。月初に非人事イベントのみが成立する場合の派閥再編0・威信画面各1、浪人2人の仕官を処理した後の全国再編1、AI臣従の吸収完了後の全国再編1、未指定の史実イベントでの再編1、途中例外後の最終再編1を直接検証した。既存の吸収共通化テストは「月次イベントは `deferFactionUpdate` を明示する」という新契約に合わせて更新。`EventManager`、`EventAction`、`common_events.js`、`AffiliationSystem` の既存契約を照合した。

`node tests/run_tests.js`：**1,355件成功・1件失敗**。失敗は配布ZIPから意図的に除いたフォント本体を要求する既知テストであり、今回の人事・派閥変更には関係しない。

本番ブラウザでの長期自然観戦は実施していない。局所fixtureの検査と長期自然観戦を混同しない。
