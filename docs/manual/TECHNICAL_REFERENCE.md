# 戦国覇道 コード構成ガイド

この文書は「どこに何があるか」を迷わないための索引です。
専門部署化は **ファイルを細かく増やすこと自体が目的ではありません**。同じ概念・計算・状態変更の正本を1か所にし、外部からの入口を少なくすることを優先します。

## 監査の目的と改修判断（最優先・作業開始前に必読）

**監査はゲームを改善するために行う。修正箇所・テスト件数・版数・作業量を増やすこと自体を成果にしない。何も改修しない結論も、正当な監査結果とする。**

1. **まず実際の到達経路を確かめる。** 通常のプレイ操作、AIの自動進行、観戦、セーブ／ロード、タイトルへの復帰など、実装済み機能から現象が起こる順序を特定する。画面がモーダルで進行を止める場合、同時に月送り・落城・死亡・婚姻などが起こると憶測で仮定しない。ゲーム中に存在しない「プレイ途中のシナリオ切替」等の操作を創作しない。
2. **人工的な状態破壊と実際の不具合を区別する。** テストから武将の所属・生死、城の所有者、年月などを直接差し替えて失敗させた場合は「人工状態変更での防御不足」と記録し、通常プレイで再現した不具合とは呼ばない。人工テストだけを根拠に修正するのは原則禁止。例外は保存データ破損やセキュリティ境界など、通常のUI操作外でも実害と対策の必要性が具体的に示せる場合に限る。
3. **改修には根拠と価値が必要。** プレイヤーが経験する症状、正常な内部処理からの到達経路、実害、既存設計との矛盾を確認し、原因の正本を特定する。修正が本当に必要か、既存の仕組みで既に安全ではないか、修正が正常系を狭めないかを先に評価する。単に「追加のガードを入れられる」ことは改修理由にならない。
4. **正常な仕様を尊重する。** 両案に合理性がある場合、前回までの設計判断を毎回ひっくり返さない。個別の特例や新しい状態正本、無意味な再検証・二重チェック、用途のない共通化を増やさない。必要な改修は最小範囲にとどめ、共通Rules/Systemの正規窓口を用いる。
5. **実際の操作から再現できるテストを優先する。** 原因修正前に実際の操作経路に近い再現テストを行い、修正後に正常系と既存の回帰を確認する。テストが失敗するよう意図的に内部データを壊しただけなら、その限界を明記する。テスト件数を増やすためのテスト追加もしない。
6. **無改修で終えてよい。** 到達性・実害・費用対効果を調べて修正の必要性を認められなかった場合、その時点で監査を終了してよい。改修のために別の不具合を探し続けない。監査時の確認範囲・判断根拠・未検証事項は必要に応じて作業記録に残す。**ユーザーが「変更がない場合は出力不要」と指定した継続監査では、製品コード・データ・マニュアル等に実際の変更がなければ、新しいZIP・パッチ・同一内容の完全版・監査報告ファイルを作成・再配布せず、無変更の結果を毎回文章で出力する必要もない。** 文書改訂や版番号更新も目的に必要なときだけ行う。
7. **報告では事実の種類を区別する。** 「通常プレイで再現」「実装経路上は到達可能」「人工状態変更のテストのみ」「静的な懸念」「未検証」を混同せず、検査で確認していない項目を「通過」と書かない。何も変更しなかった場合はコード無変更と明記する。

**r580に関する補足：** 和睦・従属交渉で姫の結婚、家臣の死亡・移籍、城の落城などが交渉画面の待機中に自然発生することは、これまでの検証では立証していない。r580の4系列の失敗はテストが条件対象の内部状態を直接変更して作ったものであり、通常プレイの発生不具合4件を意味しない。既存の防御判定は直ちに不要と断定して削除せず、正常な交渉への悪影響が確認できる場合だけ見直す。

## AI改修時の必須ルール（最優先）

AI・自動修正・今後の開発作業では、個別機能の都合より先に次を確認する。既存章に詳しい説明がある場合も、この節を入口として扱う。

1. **責務は専門部署へ寄せる。** ゲームルールは Rules / System / Service、表示は View / UI、静的DOMはHTML、静的な見た目はCSSへ置く。呼び出し元に同じ計算や状態変更を複製しない。
2. **古い処理を残して後段から打ち消さない。** 仕様変更で不要になった分岐・CSS・イベント・データ列は、参照先を整理したうえで削除する。後勝ちCSS、二重イベント、旧処理を残した強制上書きで不具合を隠さない。
3. **HTML / CSS / JavaScript の依存を最小限にする。** HTMLは構造、CSSは配置・外観、JavaScriptは状態・振る舞いを担当する。JSによる静的inline styleや、HTMLのinlineイベント属性を増やさない。PC/スマホ差は可能な限りCSSで表現する。
4. **固定論理画面を前提にUIを作る。** PCは16:9、スマホ系は9:16の論理画面を既存の等比縮小と上下左右の黒帯で表示する。内部レイアウトのPC/スマホ判定は `app_bootstrap.js` が設定する `body.is-pc` を唯一の正本とし、各画面が `innerWidth`・CSSの物理viewport幅・UAを独自に見て再判定しない。物理viewportへ直接レイアウトを合わせず、黒帯へゲームUIをはみ出させない。固定論理画面内部の寸法計算も論理CSS pxへ統一し、`transform: scale(...)` の影響を受ける `getBoundingClientRect()` の物理表示寸法と `clientHeight` / computed style 等の論理寸法を混在させない。物理座標が必要な当たり判定等を除き、一覧行高・収容行数・固定枠サイズの計算はView側で論理寸法を測る。
5. **スクロールを安易な逃げ道にしない。** 主要なゲーム画面・モーダルは原則として固定論理画面内へ収める。項目数が増える場合は、まずページ分割・タブ・表示密度調整を検討する。仕様上スクロールが適切な情報画面だけ明示的に許可する。
6. **標準モーダル操作は内容枠の外へ置く。** ［決定］［確定］［次へ］［戻る］［キャンセル］［終了］など、画面遷移や確定に使う標準操作は `modal-footer` 系で内容枠の外側・下へ置き、内容枠との間隔は原則12pxとし、`--modal-footer-gap` を唯一の正本とする。モーダル内部の補助操作・機能選択・ページ送りには詳細画面系など別用途の内側用ボタンを使い、標準確定ボタンと混在させない。
7. **古いスマホでの強制リロード回避を優先する。** 全画面Canvas・巨大ImageData・連続同期処理・不要な再描画・GPUエフェクトを増やす前に、常駐メモリと一時ピークを確認する。重い処理は必要に応じて分割しブラウザへ制御を返す。描画の健全性確認だけを目的に `getImageData()` を頻繁に呼ばない。
8. **ユーザー管理のマスターデータを単純上書きしない。** 管理の正本は `共通データ.xlsm` と各シナリオ `.xlsm/.xlsx` であり、`data/common.bin`・`data/scenarios/index.bin`・`data/scenarios/<folder>/scenario.bin` は `tools/data_converter.html` から生成する派生物として扱う。確認用の名前列・備考・参照シートは管理用Excelに残し、ゲーム実行用BINには必要列だけを出力する。武将などの個々の値をコード改修の都合で勝手に置換せず、必要な場合は管理用Excelとの意味上の差分を確認する。
9. **旧セーブ互換層を持たず、現行セーブ形式を正本にする。** 開発段階では旧形式の変換・欠損列補完・旧キー読替を積み増さない。`SaveManager` が保存する `saveSchemaVersion` と現在のスキーマが一致するデータだけをロード対象とし、構造変更時は現行スキーマ側を更新する。旧セーブを読み込むためにゲームロジックやモデルへ移行分岐を残さない。ただしユーザー管理のシナリオマスターデータを破壊的に上書きしてよいという意味ではない。
10. **変更があった場合は変更報告を残す。** 実際にファイルを変更した作業の完了時は、変更ファイルを「追加」「更新」「削除」に分け、各区分内をファイル名の昇順で列挙する。該当なしの区分も「なし」と明記する。**ファイル変更のない継続監査には報告書・差分・再梱包を必須としない。**
11. **button系SEは共通button監視を正本にする。** 通常の `<button>` の決定/戻る音を各Viewの `onclick` から重ねて `playSE()` しない。通常決定は共通既定値、戻る/キャンセルは共通ルールまたは `data-se="cancel.ogg"`、選択・切替など特殊音は `data-se` で宣言する。合戦コマンド・会話画面タップ・非button要素など、共通button監視の対象外だけ各専門Viewが個別SEを担当する。 汎用の二択・切替操作は `.ui-toggle-btn`、兵科選択だけは `.troop-type-btn` とし、見た目を共有しても意味上のclassを流用しない。
- 固定DOMへ戦闘・画面表示のたび `addEventListener()` する場合は、bind-onceまたは前回handlerの明示解除を必須とする。画面を閉じてもDOMが再利用される野戦等では、古いクロージャを蓄積させない。
12. **開発版番号は `GameConfig.Meta.Version` を正本にする。** タイトル左下の版表示へ値を直書きせず、起動時に `app_bootstrap.js` がこの値を反映する。配布・確認用ZIPの版を上げる場合はこの1か所も同じ版番号へ更新し、古いファイルが残っていないか実機で即確認できるようにする。
13. **履歴は `HistorySystem` を正本にする。** 履歴は単なるUIログではなく、年月・本文・関係勢力・種類を持つゲーム記録として管理する。自国/全国の振り分けやセーブ継続はこの構造化データから行い、自国が関与する履歴は自国、自国が関与しない履歴は全国のどちらか一方だけへ表示する。交易・独立/寝返り/謀反・臣従・外交婚姻の処遇・人質処遇など複数勢力が当事者となる出来事は、本文から推測せず当事者の `clanIds` を記録時に明示する。UIの一時案内を履歴へ混ぜない。面談・情報取得・選択促進など、後から振り返る必要のない表示は履歴対象外とする。
14. **指南書はプレイヤーが知り得る範囲を守る。** 画面や結果メッセージで直接確認できる情報は明確に説明し、繰り返し遊べば傾向として感じ取れる仕組みは定性的な表現に留める。野望・義理・内部忠誠値・承認欲求など非公開パラメータ、内部計算式・閾値・倍率・確率は指南書へ出さない。文章は説明・案内調を基本とし、「見てください」「確認してください」などの命令口調を避ける。 同じ内容を複数の記事やFAQへ重複掲載せず、説明の正本となる項目へ統合する。FAQは別記事と同じ説明文を繰り返す場所にしない。
15. **ダイアログの引き渡し先を区別する。** 会話→会話・外交結果のように連続して同じダイアログ系UIへ進む場合は、旧画面を次画面の可視化まで保持する handoff を使う。一方、出陣演出・戦場・マップ選択・一覧モーダルなど非会話画面へ進む選択は、旧ボタンや暗幕を残したまま次処理を始めず、`closeBeforeOk` / `closeBeforeCancel` / 選択肢の `closeBeforeAction` で入力画面を先に閉じてから遷移する。月終了、観戦開始・終了、タイトル/ロード、評定開始・終了のように確認後すぐ通常画面や専用モーダルへ移る操作も同じ境界とし、確認ダイアログのhandoff猶予を次画面へ重ねない。固定ms待ちで両者を一律処理しない。
16. **一般名称として場所を指す時は「拠点」を使う。** 地図上の地点には城だけでなく館・御所なども含まれるため、UI・指南書・システムメッセージ等で地点そのものを一般化して指す場合は「城」「敵城」「自領の城」「通常の城」ではなく「拠点」「敵拠点」「自領の拠点」と表記する。拠点固有名、人物の会話台詞、および「城主」「城壁」「攻城戦」「籠城」「居城」「落城」「入城」など一語として別の意味・歴史用語を持つ表現はこの置換対象にしない。内部の `Castle` 型・`castleId` 等のコード識別子まで機械的に改名しない。
17. **ロード可否は「実際に現行形式として読み込める保存」があるかを正本にする。** IndexedDBのキーや値が存在するだけで「続きから」「ロード」を有効にしない。`SaveManager` が手動セーブ・オートセーブの双方を復号し、現行 `saveSchemaVersion` と復元前の厳密な構造検査を通った保存だけをロード可能と判定する。タイトル画面・システムメニュー・ロード一覧は同じ判定を共用し、未検査・旧形式・破損データしかない場合はロード操作を選択不可にする。

18. **ロード幕の解除はUIManager共通窓口を正本とする。** ロード幕を使う画面遷移（タイトル初期表示／タイトル復帰／シナリオ開始／セーブ復元）で `hideLoadingScreen()` を同期的な `.hidden` 付与として扱わず、`await` して完成画面へ引き渡す。`UIManager._waitForLoadingPresentation()` は、ロード幕を残したままフォント・現在表示中の画像（可視 `img` と可視要素のCSS背景・`::before` / `::after` の背景画像は `load` と `decode` を完了させる。`img.complete` だけではdecode完了と判定せず、同一要素・同一画像のdecodeは重複実行しない）・画面／モーダルの矩形を確認し、`MutationObserver` で新しい子要素や属性変更を自動捕捉して、実paint機会を複数回通した後だけ解除する。後から画面の子要素やモーダルを追加しても個別の待機対象列挙は不要。非同期に子要素を組み立てる場合だけ、処理開始時に `UIManager.trackLoadingTask(promise)` へその完了Promiseを登録すること（登録せずにロード幕解除後から始める非同期処理は検知不能）。固定msの待機や各画面独自のロード解除を追加しない。新しいロードの世代が始まったとき、前のロードの終了予約が新しい幕を消してはならない。エラー案内など従来の非await呼び出しも、共通窓口がレイアウト確定まで幕を保持する。画面・モーダルがロード幕なしで開く通常操作は別の既存表示責務のままにする。低メモリ端末対策として、非表示画像やlazy画像の完了は強制的に待たず、大量のCanvasの再読み込みは行わない。

19. **タイトルからゲーム本体への固定DOM切替はUIManagerを正本とする。** `GameManager.loadScenario()` と `SaveManager` のセーブ復元は、`#title-screen` と `#app` の可視状態を直接変更せず `UIManager.showGameSurface()` に委譲する。状態の `phase`、ロードの世代管理、地図描画、ロード幕解除は従来の各責務を維持する。ロード完了待機をこの表示切替メソッドに混ぜない。新しい開始・復元経路を追加する際も同じ窓口を使い、画面切替の複製を増やさない。
20. **タイトル復帰時も固定画面の可視状態はUIManagerを正本とする。** `UIManager.returnToTitle()` が旧シナリオの戦争／ターン世代とモーダル・地図資源を整理した後、`UIManager.showTitleSurface()` で `#app` を隠し `#title-screen` を表示する。コマンドメニューや大名選択の「シナリオへ戻る」等は `#app` を個別に隠さず、既存の `returnToTitle()` を呼ぶ。ロード幕表示の先行・画面寿命の確認・ロード完了判定・新規シナリオ開始の `showGameSurface()` は従来どおり維持し、二方向の切替を機械的な単一関数へ混在させない。


21. **非同期画面遷移の後続処理は完了結果を確認する。** `UIManager.returnToTitle()` は通常完了時に `true`、TurnManagerの後発遷移により失効した時や遷移不能時には `false` を返す。タイトル復帰後にさらにシナリオ選択・別画面生成などを実行する呼出元は、必ず戻り値が `true` の場合だけ後続処理へ進む。`await` で復帰処理の終了を待つだけでは、失効による早期終了も正常完了と見分けられない。呼出元に独自の世代管理を複製せず、共通窓口の結果を利用する。画面切替、ロード幕、セーブ復元の世代管理は従来の正本を維持する。

UI固有の細則、低メモリ端末対策、各Systemの正本は以下の各章を参照する。新しい実装がこの節と衝突する場合は、場当たり的な例外を追加する前に責務・UI構造そのものを見直す。


## 分割ルール

新しいJSファイルは、原則として次のどれかを満たす場合だけ追加します。

1. 複数の既存ファイルから同じ処理が必要になる。
2. 現在のファイルに明確に別の責務が混ざっている。
3. 単体でテストでき、再利用されるまとまりである。
4. まとまった独立領域が大きくなり、元ファイルの全体像を損ねている。
5. 他部署から参照される明確な窓口（Manager / Rules / Service / View）になる。

数十行しかなく、そのファイルからしか使わない補助処理は、原則として元の部署内に置きます。

## 入口・基盤

- `js/app_bootstrap.js` — ブラウザ起動処理。タイトル用軽量フォントの先行準備と本体フォントの遅延・ロード幕内完了待機、固定HTMLボタン、タイトル版表示、viewport、離脱警告。
- `js/audio.js` — BGM/SE再生と音量設定反映の正本。Howlerのmin版が読めない場合の通常版フォールバックもここで管理し、一時SE用Howlは再生終了・読込失敗時に解放する。BGMのループ開始・終了はカタログ値を独立して適用し、`start: 0` でも終了点を無視しない。再生中の音量変更はHowler内部プロパティから曲名を推測せず `currentBgmName` を正本にする。タッチ端末の長尺BGMは `data/music/bgm_mobile/*.m4a` をHowlerのHTML5 Audio経路でストリーミングし、Web Audioの巨大な全曲PCM AudioBuffer常駐を避ける。mobile AACには各曲の `baseVolume` を音源側へ焼き込み、HTMLMediaElement.volumeが固定される古いiOSでもBGMだけ過大音量にならないようにする。PCは従来のOGG/Web Audio経路を維持する。 iOS/iPadOSでAudio Session APIが利用できる場合は `ambient` を明示し、HTML5 BGMを含むゲーム音全体をRing/Silent（マナーモード）に従わせる。音声ポリシーは `audio.js` 以外へ重複実装しない。
- `js/config.js` — ゲームルール・バランス値と開発版メタ情報の正本。ユーザー個人の設定は置かない。タイトルの版番号は `GameConfig.Meta.Version` だけを参照する。
- `js/constants.js` — 状態文字列と、複数状態をまとめた意味判定（LifeStatusRules / BushoStatusRules / DiplomacyRules）の正本。
- `js/user_settings.js` — 通知・歴史イベント・オートセーブ・音量などユーザー個人設定とlocalStorageの正本。
- `js/game.js` — GameManager。ゲーム全体の司令塔。専門部署へ仕事を振る。
- `js/turn_manager.js` — 月初・各拠点ターン・月末の進行順を管理。月次の具体的な計算式は持たず、FactionSystem / EconomyRules / DomesticRules / PersonnelRules / AIStaffing 等へ委譲する。
- `js/data_manager.js` — `data/scenarios/index.bin` のシナリオ定義、`data/common.bin` の共通マスター、`data/scenarios/<folder>/scenario.bin` の年代別stateを読み込み、IDで結合して既存モデルへ渡す。実行時はCSVを読まない。共通マスターはシナリオ切替でも再利用できるようキャッシュし、年代別stateだけを切り替える。城色画像は各城の種点座標だけを帯状解析し、国境画像は国IDマップへ変換する。その後、各国のピクセルを国内の最寄り城へ割り当てて領土用の城IDマップを構築する。巨大RGBAや全画面BFSキューは常駐保持せず、地図UI・イベントは同一TypedArrayを共有する。タイトル復帰・シナリオ切替時は `releaseMapResources()` を正規窓口として旧国/城IDマップの参照を切り、新しい地図生成時のピークメモリへ重ねない。
- シナリオ登録の正本は `data/scenarios/index.bin` とし、`SCENARIOS` は起動時にそこから展開する実行時配列に限定する。削除済み・開発用シナリオをコードへ登録だけ残して選択可能にしない。シナリオ選択UIには実データと分離した選択不可のダミースロットを置いて複数件時の密度を確認できるようにし、`tests/visual/guide.html` の確認用モックも同じ考え方で維持する。4件以下は一列の見た目を保ち、5件以上では同じカード意匠のままPC・スマホとも2列へ切り替えて、少数時の間延びと件数増加時の縦スクロールをどちらも抑える。ダミーを `SCENARIOS` や保存対象のシナリオとして扱わない。
- **シナリオ定義の入力境界:** `DataManager.loadScenarioDefinitions()` は `tools/data_converter.html` の `scenario_info.folder` と同じ `[A-Za-z0-9_-]+` を実行時にも検証する。不正な `index.bin` は部分登録せず拒否し、`loadAll()` のURLを構築する前にも登録済みの安全なfolderか確認する。シナリオ選択の名称・説明は `UIManager.showScenarioSelection()` の表示境界で `textContent` として描画し、選択・ダミースロット・改行表示の従来構造は保つ。

### 管理用Excelと実行用BIN

- 共通側は人物・姫・勢力の登録情報、拠点の地理/接続情報、国、官位、汎用姫名を持つ。配偶関係、所属、所在、忠誠、当主、城名や城パラメータなど開始年代で変化する値はシナリオ側へ置く。
- 勢力は `clans_master` に共通登録し、各シナリオの `clans_state.enabled` で登場可否を決める。外交は `diplomacy` の1関係1行を正本とし、読込時に既存 `Clan.initDiplomacy` 形式へ変換する。
- **シナリオの勢力所属変更では、史実上の独立・存続だけで所属を分離しない。** その勢力・拠点が地図上の領土連続性や進軍経路の接続を担っている場合、独立勢力化によって既存の接続が切れないかを必ず先に確認する。特に1570年姉川シナリオの北畠家は、近畿方面への織田家の接続を維持するため織田家所属のままとし、史実上の名目的存続を理由に北畠家を独立有効化しない。勢力変更時は `castles_master` の接続・`map_graph` の到達性・隣接する同一勢力領の連続性をセットで監査する。
- **シナリオ作成・年代調整では共通データを原則参照専用とする。** 人物同定・登場年・没年・系譜・列伝など共通マスター側の修正は、明示的な依頼がない限りシナリオ作業側から変更しない。
- **シナリオ開始時の有効な通常勢力は軍師を必ず1人だけ持ち、軍師と城主を兼任させない。** 軍師候補は共通マスターの `startYear` / `endYear` と開始年月を照合し、開始時点ですでに死亡済みの人物へ古いシナリオ差分から軍師フラグを戻さない。勢力吸収・所属変更時も旧勢力の軍師フラグを持ち越さず、移籍後の家中全体で再選定する。
- **初期軍団は城側の `legionId` を大名家内の `Legion.legionNo` として扱い、`ownerClan + legionNo` に対応する軍団行が存在することを必須とする。** 軍団長は同勢力所属とし、所属城・城主との整合を取る。所属城を失った孤立軍団行を残さない。`kunishuClan.daimyoRelations` の数値参照は通常大名家の `clanId` を指し、諸勢力IDとして解釈しない。
- **シナリオ初期配置では可能な限り城主を設定するが、城主不在（`castellanId=0`）も有効なゲーム状態である。** 史実の城主が共通マスター未収録の場合は、同じ地域・勢力圏の収録済み有力武将を代理で置くか、人物に適した近隣の代表城へ名称を置き換えてよい。ただし城主必置をゲームの不変条件とはせず、空席を理由にイベント・勢力再編・城の所有権変更を延期・中止しない。勢力圏・地理・進軍構造と人物の消失防止を優先する。
- **シナリオ編集時も既存の「大名＝居城の城主」仕様を維持する。** 有効な通常勢力では `clans_state.leaderId` の武将が所在する `castleId` をその大名の居城とし、その拠点の `castellanId` は必ず同じ `leaderId` にする。未収録の史実本営を別の収録拠点で代表する場合も、この対応を崩して「大名は同居するが城主は別人」という例外を作らない。代表拠点を変更・改称する場合は、当主・城主・所有勢力・在城を一組で確認する。
- **同一家・同一勢力を通常大名家所属と諸勢力（`kunishuClan`）で二重表現しない。** 1570年神保氏のように通常勢力の傘下として代表城・城主を置く場合、同じ家の諸勢力IDと `belongKunishuId` を残さない。
- **功績は1560年シナリオの階層を基準に年代進行で再評価する。** 現役大名は原則1500、弱小大名は1000、将軍級は2000、後継候補は概ね1000/700/500。失領・追放・隠居・他家保護などで大名権力を失った元当主は200を基本とする。一方、従属後も城・家臣団・独自行動力を保つ地域領主は300～500、松永久秀・宇喜多直家のように従属下でも実力上ほぼ独立する例は個別判断で高位を維持できる。1570側の既存値を自己参照せず、1560正本の配分と1570時点の身分変化を基準にする。
- **1570年姉川シナリオの北畠氏は織田家勢力内の地域勢力として表現する。** 霧山城は北畠具房を城主、北畠具教は同城所在の隠居（功績200）とし、安濃津城枠は木造城へ置換して1569年に織田方へ転じた木造具政を城主とする。北畠家を独立勢力へ戻さない。
- 拠点共通マスターはマップ上の拠点スロットとして扱い、`id`・`sortNo`・`provinceId`・`castlesColorCode`・`adjacentCastle` を共有する。名称、所有、城主、軍団、兵力・物資・内政値などは `castles_state` が持つ。
- **年代別の城名変更は同一地理スロットの時代差表現として行い、別地域の城を便宜だけで移植しない。** 1570年姉川では、ID246を栗太・野洲方面の多喜山城として山岡景隆を代理城主に置き、ID27を大津・坂本方面の宇佐山城として森可成を置く。1571年以降に坂本城を表現する場合も、同じ大津・坂本方面スロットの年代差として扱う。
- 国衆と軍団はシナリオ固有データとして `scenario.bin` に格納する。
- `tools/data_converter.html` は共通Excel1件とシナリオExcel1件以上を同時に受け付ける。必要シート/列、ID重複、master/state不整合、Excelエラー値を検証し、エラーがある場合は壊れたBINを出力しない。
- BIN schema version は `DATA_SCHEMA_VERSION` で検証する。形式は `sengoku-common-v1` / `sengoku-scenario-index-v1` / `sengoku-scenario-v1`。

- `js/save_manager.js` — セーブ、ロード、IndexedDB、オートセーブ。`saveSchemaVersion` を現行保存形式の境界とし、旧形式の移行・マスター同期は行わない。ロードはゲーム状態へ触る前にスキーマ・保存構造・主要ID参照を事前検証し、復元開始後の実行時失敗だけ、復帰前に「タイトルへ戻ります」と案内してから安全にタイトルへ戻す。手動セーブの暗号化Uint8Arrayと低メモリ用オートセーブの構造化オブジェクトは、いずれも同じ現行スキーマを保存媒体だけ変えて保持する。 タイトル・システム・ロード一覧の有効判定も `isLoadableSaveData()` / `readSaveSlots()` を通し、保存値の存在だけを直接見ない。
- `js/history_system.js` — 行動履歴の正本。年月・本文・関係勢力・種類を構造化して保持し、自国/全国の排他的な振り分けとセーブ復元を担当する。通常UIの一時メッセージを履歴の保存先として使わない。
  - 全国履歴は全知情報ではない。調略など秘匿行動は、自家が実行した場合、または自家が標的となり発覚した場合だけ通常の調略履歴として記録する。他家同士の秘密工作は発覚していても載せず、引抜成功による武将の所属変更など外から確認できる結果だけを原因を伏せた結果履歴として残す。戦争は開戦元・援軍参加・最終勝敗・落城/防衛・勢力変化を構造化して記録し、兵糧切れや負傷兵復帰など戦場内の一時表示は履歴へ混ぜない。月区切りは表示側で生成し、履歴件数を消費しない。
- `js/event_manager.js` — 通常イベントの発火管理に加え、常駐イベントの状態遷移（false→true / true→false）とセーブ継続状態を管理する。歴史イベントOFF時は適用中の `historical_` 常駐効果を解除し、再ON後は各イベント本来の登録タイミングで条件を再評価する。歴史上の条件・効果量・対象は `js/event/historical_event.js` 等のイベント定義側、実際の数値書換は各専門Systemへ委譲する。 `UserSettings` は設定変更を汎用通知し、`GameManager` が歴史イベント設定だけを `EventManager` へルーティングするため、設定UIは常駐効果の実処理を直接呼ばない。

## ルール・共通計算

- `js/domestic_rules.js` — 内政、訓練、徴兵。城の士気・訓練は共に「通常コマンド上限100／戦争由来のみ内部120／UIゲージ100%基準100」の三層仕様とし、`WarParams.Military` の `MaxMorale*` / `MaxTraining*` を正本にする。100超の値を兵施し・通常訓練・AI内政で100へ巻き戻さない。
- **城内人物と城主家臣を混同しない。** `getCastleBushos()` と `castle.samuraiIds` は同じ城に物理的に存在する人物全員を表し、浪人・諸勢力所属者・例外的な他家武将を含み得る。給金・役職成長・通常大名家の防諜・AI配置人数・撤退先評価・落城時の捕虜/退避・後継者不在滅亡・AIの官位/上洛判断など『城主家に属する武将』だけが効果を持つ処理では、`clan === castle.ownerClan`・通常所属・活動中を明示して絞る。諸勢力蜂起でも、蜂起した諸勢力や同居する別諸勢力を旧城主家臣として処理しない。
- `js/economy_rules.js` — 収入、交易、購入価格、経済計算。米相場 `marketRate` は「金1で得られる兵糧量」を正本とする（例: 2.0なら金1＝兵糧2.0）。基準相場は2.0前後とし、値が高いほど米が安く、低いほど米が高い。プレイヤー売買・AI売買・最大取引量・相場表示・災害/豊作/戦争による相場変動はすべてこの意味へ統一する。
- `js/personnel_rules.js` — 相性、調査、登用、褒美。人物関係は専用の「協調性」を持たず、相性差を主軸に義理・野望を補正として扱う。
- `js/portrait_rules.js` — 武将の年代別顔変更文字列の解釈を一元管理する。数字条件（例 `1553:face.webp`）から指定年時点の顔を決定し、新規ゲーム開始・年次更新で共用する。`daimyo:` や歴史イベント等の非年代条件の発火判断は各専門Systemへ残す。
- `js/loyalty_insight_rules.js` — 忠誠の段階と本人による表面上の偽装を一元管理する。智謀70～89は1段階、90以上は2段階だけ高く見せる規則を面談と軍師所見で共有し、各画面が実忠誠から独自に危険色や見かけ忠誠を計算しない。
- `js/ai_domestic_priority_rules.js` — AIの城壁修復・石高開発・鉱山開発の基礎スコアと、石高／鉱山の性格・攻撃準備中補正を一元管理する。AI本体と面談の「方針について」は同じ評価式を参照し、面談専用の別スコアを作らない。
- `js/game_math.js` — 複数部署から使う小さな汎用数値処理。兵士合流時の士気・訓練度の加重平均（算術のみ）も `weightedAverageFloor()` を正本とし、各処理が独自の除算・端数切捨て式を複製しない。受入可能人数・能力値の上限下限・欠損値の補完といった業務規則は既存の各Systemで管理する。小さいが共通依存なので独立を維持。
- `js/stat_presenter.js` — 能力ランク・武将肩書きなど表示用整形。小さいがRules/ModelへHTML・表示責務を戻さないため独立を維持。
- `js/busho_list_sort_rules.js` — 武将一覧で共用する既知情報の検索・ソート規則。名前・所在・身分など画面横断で同じ意味を持つ並び順をここへ集約し、敵能力の秘匿・推定値や選択済み優先など画面固有事情は各View側に残す。身分ソートだけは同身分内の第二キーに非公開の功績を同じ昇降方向で使い、降順では高功績、昇順では低功績を先にして、数値を明示せず並びから実績を薄く推測できるようにする。
- `js/conversation_standing_rules.js` — 会話上の人物・大名家の格を一元管理する。家中身分、官位、功績、大名家威信、将軍/将軍候補の特殊権威は別軸で保持し、一つの巨大な格スコアへ潰さない。大名家同士は征夷大将軍の別格性→官位の `rankNo` を優先し、同格官位または双方無官の時だけ威信比を会話上の上下へ使う。左馬頭の将軍候補性は人物本人への特別な礼遇に使うが、大名家同士の官位比較そのものを `rankNo` より先に逆転させない。使者は主君の外交上の格を背負いつつ本人の軍師/国主/城主等の身分・官位・功績でも礼遇を微調整する。将軍・将軍候補本人が他家所属になっても公的権威を失わせず、使者時に主君より本人の格式が高い場合は「主君様の名代」として本人を下げない。功績は非公開値のまま、面談等で呼称・敬語・実績を匂わせる表現だけに使い、数値や厳密な段階を露呈させない。 無官人物の会話呼称もここを正本とし、原則は姓＋敬称、話し手と対象が同姓の場合は一門なら諱＋敬称、一門でなければフルネーム＋敬称として同姓人物の識別と当時らしい諱回避を両立する。面談で第三者が質問者である当主と同姓の無官武将に言及する場合は、『織田殿』等が当主本人を指すように聞こえるため、より優先される血縁・役職呼称がなければ一門関係にかかわらずフルネーム＋敬称で識別する。特殊称号・官位呼称はこの無官ルールより優先し、官位で呼ぶ場合は姓を付けず『修理亮殿』『参議様』のように官位名＋敬称だけを使う。実父系の具体的血縁は `realFatherId` を正本として扱う。`adoptiveFatherId` は養父・義父に加えて武将として登録された母親の参照にも使われるため、会話では直接参照だけを使う。子側から参照先を見る時は参照先が `female=true` なら『母上』、それ以外は『義父上』、逆に参照先本人から子を見る時は年少親族として官位があれば敬称なしの官位名、無官なら諱を呼び捨てにする。`adoptiveFatherId` から兄弟・祖父等の派生関係は推論しない。`realMotherId` は姫データ参照であり武将同士の会話判定には使わない。本人同士の直接会話では面談・外交とも同じ近親呼称を使い、官位・身分より年長親族への家族呼称を優先する。`adoptiveFatherId` の直接参照が女性なら『母上』、男性なら『義父上』、実父系では子→実父は『父上』、弟→実兄は『兄上』、孫→実祖父は『祖父上』、父方の伯父・叔父は実父との年齢差が確定できる場合だけ『伯父上』『叔父上』とする。逆向きの実父→子・兄→弟・祖父→孫、および義父/武将母→子は年少親族として、官位があれば敬称なしの官位名、無官なら諱を呼び捨てにする。伯父・叔父側から甥・姪を見る逆方向も `realFatherId` だけから確定し、同じ年少親族呼称へ流す。第三者が当主に親族について言及する場合は逆に特殊称号・官位を優先し、無官時だけ『御父君』『御子息様』『御兄君』『御舎弟』『御祖父君』『お孫様』『御伯父上』『御叔父上』を使う。面談の『他者について』では、答える本人から見た近親関係をさらに優先し、`adoptiveFatherId` の直接参照が女性なら『母上』、男性なら『義父上』、実父系の父・実兄・祖父は官位に関係なく『父上』『兄上』『祖父上』、実弟・実子・実孫は官位持ちなら官位名を敬称なし、無官なら諱を呼び捨てにする。無官の軍師は、質問者である当主・話者のどちらの一門でもなく、より優先される血縁呼称もない場合だけ『軍師殿』と呼ぶ。
- `js/dialogue_text_rules.js` — 会話文の表示組版を一元管理する。元の台詞データは変更せず、実際に鉤括弧で閉じる会話が `「…。」` になった場合だけ `」` 直前の終端句点を省く。軍師・外交・イベント等の通常ダイアログと面談専用会話で同じ規則を使い、各Viewへ同じ正規表現を複製しない。
- `js/skill_manager.js` — 技能文字列の解釈と技能効果の唯一の窓口。

- `js/castle_manager.js` — 城主・城所有者など拠点状態の管理。

- `js/map_generator.js` — 地図描画用データ生成。

### 重要状態の書き換えルール

- 実行中の `busho.clan` / `busho.castleId` は `AffiliationSystem` だけが直接書き換える。通常は `joinClan` / `becomeRonin` / `moveCastle` を使う。
- **在城履歴の更新責務:** `stayHistory` と `arrivalTurn` の計算・保存は `FactionSystem.handleMove()` が所有するが、その呼び出しは `AffiliationSystem` が一元管理する。通常の城間移動は `moveCastle()` が実移動時だけ記録し、利用側（外交・AI・戦後・人事・イベント）から `FactionSystem.handleMove()` を直接呼ばない。移動元を確定できない捕虜・引抜等は履歴の旧城期間を推測せず0を渡す。家督・国主継承など、名簿と役職を専用処理が持つ低レベル転任だけ `setCastleIdRaw(..., { recordStayHistory: true })` と明示し、その他のraw更新では履歴を勝手に更新しない。
- 実行中の `busho.isGunshi` は `AffiliationSystem.clearGunshiRole()` / `appointClanGunshi()` だけが変更する。`appointClanGunshi()` は同勢力の既存軍師をすべて解除して一人だけを任命し、`setClanIdRaw()` は所属勢力が変わる時点で軍師役職を自動解除する。軍師役職を寝返り・独立・吸収先へ持ち越さない。シナリオ初期読込の `models.js` / `data_manager.js` だけは例外。
- 独立・歴史イベントなど、周辺の名簿や役職処理を呼び出し側が既に管理している特殊処理だけ `setClanIdRaw` / `setCastleIdRaw` を使う。
- 実行中の `castle.ownerClan` は `CastleManager` だけが直接書き換える。通常は `changeOwner`、副作用を起こしたくない特殊ロールバックだけ `setOwnerIdRaw` を使う。
- `Castle.legionId` は大名家内の軍団番号（`Legion.legionNo`、0〜8）であり、ゲーム全体で一意な `Legion.id` とは別物。城から軍団モデルを引く時は `clanId + legionNo` で照合し、`castle.legionId === legion.id` の比較や `disbandLegion(castle.legionId)` を行わない。
- `busho.isCommander` は `Legion.commanderId` から導出する実行時キャッシュとする。同一人物を複数軍団の `commanderId` に登録せず、セーブ復元時も保存済みフラグを信頼せず現行 `Legion` 一覧から再構築する。
- `busho.isCastellan` は `Castle.castellanId` と対になる実行時キャッシュとして扱う。城主交代時は旧 `castle.castellanId` が指していた人物のフラグだけを解除し、城内の無関係な同居者へ一律操作を広げない。セーブ復元時も保存済みフラグを信頼せず `Castle.castellanId` から再構築する。
- `Castle.samuraiIds` は在城名簿なので、同一武将IDを重複させず、掲載する武将の `busho.castleId` と一致させる。現行セーブは復元前にこの参照整合性を検査し、欠損・重複・別城参照を黙って補完しない。
- `models.js` と `data_manager.js` のデータ生成・初期読込は上記ルールの例外。
- 武将の `active / ronin` は活動・所属状態として `AffiliationSystem.setActivityStatusRaw` が低レベル書換窓口を持つ。通常処理は joinClan / becomeRonin 等の高レベルAPIを使う。
- 武将・姫の `dead / unborn` は生死・登場状態として `LifeSystem.setLifeStatusRaw` が低レベル書換窓口を持つ。武将の死亡後処理は現行の `executeDeath()` を使い、廃止済みの `processDeath()` は呼ばない。
- 武将の実行中 `endYear` は `LifeSystem.setLifespanModifier()` / `removeLifespanModifier()` だけが変更する。面談・イベント側は「対象・条件・何年変えるか」を所有して LifeSystem へ依頼し、`models.js` は本来の没年・討死フラグ・補正一覧というデータだけを保持する。シナリオ共通ルールである討死武将の初期延命だけは `LifeSystem.initializeBattleDeathLifespans()` が所有する。補正は `sourceId` ごとに識別して積み重ねられる。既存ゲーム仕様上の組合せ制約（例：討死初期延命済み武将へ医師延命を重ねない）はLifeSystemの意味問い合わせAPIを介して判定し、呼び出し側へ内部sourceIdを漏らさない。`endYear` が変わった瞬間に `LifeSystem.recalculateBushoAgeStats()` で寿命前能力低下も同期する。
- 姫の `unmarried / married`、軍団やAI作戦の `status` は別概念なので、上記と同じSetterには混ぜない。

## モデル境界

- `js/models.js` — 保存・ゲーム内データ構造そのもの。ゲーム全体の司令塔 `window.GameApp` を直接参照しない。武将モデルは `originalEndYear` / `endYear` / `isKilledInBattle` / `lifespanModifiers` を保持するが、「討死なら延命する」等のゲームルールは実行しない。
- 武将能力値の一門+5は既存getter互換のため、`GameManager` が `Busho.configureRuntime()` へ「大名を取得する関数」だけを注入する。モデルからはGameManager全体へアクセスしない。
- 武将肩書きのような表示判断は `StatPresenter`、城・軍団など周囲のゲーム状態を使う判定は利用側/Systemへ置く。
- 一門関係の再構築は `FamilyLinker.rebuildAllFamilyIds()` を正規窓口とし、各人物がゲーム全体の名簿を取りに行かない。

## コマンド

- `js/command_catalog.js` — コマンドメニュー構造・実行条件・コマンド仕様表の正本。UI表示とCommandSystemが同じ定義を参照する。
- `js/command_system.js` — コマンド開始、汎用の対象選択・数量入力・実行フローの司令塔。仕様表、セーブ/ロード画面、開戦準備そのものは持たない。
- `js/save_load_view.js` — セーブ/ロードのスロット選択画面。保存形式や復号は知らず、`SaveManager.readSaveSlots()` から復号済みデータを受け取る。 外部からロードされた保存データの勢力名・シナリオ名・保存日時は表示専用テキストとしてHTMLエスケープし、縮小地図はゲームが生成するbase64ラスター画像だけを許可する。スロットのレイアウトや表示順は変更しない。 IndexedDBの読込例外は真の空スロットと区別し、`readError` を受けたスロットは保存・ロードとも選択不可として「読込エラー」を表示する。読込失敗を `NO DATA` として上書きさせない。読込自体は成功しても現行形式として復元できない既存レコードは `invalidData` として「読込不可」を表示し、空きとは偽らない。開発中は旧セーブ互換を持たないため、明確な消失警告を確認した場合だけ上書き再利用できる。
- `js/save_manager.js` — IndexedDB・暗号化/復号・保存データ形式・ロード事前検証の正本。 手動の同一保存スロットへ非同期の複数要求が重なった場合、保存先ごとの直列処理をSaveManagerが唯一の正本として管理する。入力遮断用save-guardの参照カウントだけを排他制御と誤認しない。順番待ちの要求は開始時のターン世代・シナリオが失効すれば破棄し、古いゲーム状態を新しいシナリオのスロットへ書き込まない。別スロットやファイル保存には不要な大域ロックを掛けない。UIが `loadFromDB` や `_decryptData` を直接触らない。`saveSchemaVersion` が現行値と一致し、必須配列・年月・シナリオ・AI作戦構造・主要ID参照が有効な保存だけをロード可能とする。旧形式の作戦変換、旧宿敵配列の読替、欠損した諸勢力タグの推測、武将マスターのロード時同期は行わない。復元開始後に画像/Canvas等で失敗した場合だけ入力状態を解除し、「タイトルへ戻ります」と利用者へ案内してからタイトルへ安全復帰する。 手動・オートセーブのどちらかにこの検査を通る保存が1件以上ある場合だけ `game.hasSaveData` をtrueにし、タイトルとシステムのロード操作へ同じ結果を渡す。 タイトルでの非同期ロード可否確認が画面寿命を失った場合は、その古い判定結果を `game.hasSaveData` へ反映しない。手動保存の実行開始時にも保存先のIndexedDB読込を確認し、スロット一覧表示後に保存領域が不調になった場合は旧データ保護のため書込みを中止する。余分な大容量スナップショットを二重保持しないよう、この確認は新しいセーブデータ生成前に行う。直接ロードでのDB読込例外も空データとして扱わず、再試行可能なエラーとして案内する。 「続きから」も `readSaveSlots()` の `readError` / `invalidData` を正本として、読込エラー・非対応の既存レコード・真の空欄を区別して案内する。有効な保存が1件でもあれば従来どおり最新の保存を読み込む。

- **国主任命は候補画面の絞り込みだけで完了条件としない。** `CommandSystem.executeAppointLegionLeader()` の実行直前に、候補の生存・所属・現役国主との競合と、家ごとに管理する `Legion.commanderId` の席次占有を再確認する。選択後に状態が変化していた場合は武将移動・城主更新より前に中止し、別軍団の国主を二重登録したり、占有済みの軍団国主を上書きしたりしない。国主の正本は `Legion.commanderId` であり、`isCommander` は補助キャッシュとして扱う。既存の「大名＝居城城主」保護と通常任命経路は維持する。

`command_catalog.js` と `save_load_view.js` はそれぞれ約700行/300行の独立した責務で、`command_system.js` の全体像を大きく損ねていたため分離する。小さなコマンド種別ごとには分割しない。

## 戦争

- `js/war.js` — WarManagerの主要な入口。攻城戦・野戦で共通のホーム補正は `WarSystem.calcHomeBonusMultiplier()`、大名家所属武将の戦争時忠誠加算は `WarSystem.calcLoyaltyBattleBonus()` / `calcGroupLoyaltyBattleBonus()` を正本とする。忠誠補正は能力値自体を書き換えず、攻防能力へ `√忠誠 × War.LoyaltyBonusFactor` を1回だけ加える。諸勢力・浪人には適用しない。攻城戦が決着条件へ入る時は、ラウンド開始時点ですでに防御・士気・兵数が0でも、プレイヤー参加戦では終了理由を表示してから戦後処理へ進む。
- `js/war_preparation_controller.js` — 出陣準備・自軍援軍・他勢力援軍・開戦直前UIの司令塔。CommandSystemやAI等はここから開戦準備を開始する。

- **落城後の兵数吸収は実際の受入人数で能力値を算出する。** 通常の拠点制圧時は攻略本隊を優先して最大99,999人まで収容し、旧守備兵とその回復兵は残りの空き枠分だけ吸収する。士気・訓練度の加重平均も受け入れた攻略兵・守備兵だけで計算し、旧来の「攻略軍の値を下回らない」条件は維持する。表示上の吸収人数も実際の人数を使う。攻城損害・負傷兵回復率・軍馬鉄砲の扱いをこの補正の理由で変更しない。
- `js/war_effort.js` — 攻城戦・戦争進行の既存大規模処理。戦後に攻略軍を別城へ一括移動する場合は途中の城主再選を保留し、全員の移動完了後に出撃元・占領先それぞれ1回だけ城主を確定する。今後の整理候補。
- `js/field_war.js` — 野戦。Rules / View / AI がまだ混在しており今後の整理候補。野戦終了通知は「終了時点で残っているプレイヤー部隊」ではなく「その野戦にプレイヤーが参加していたか」を保持して判定し、総大将撃破・兵糧切れ・AI撤退などで無言のまま次段階へ進めない。 野戦AIはターゲット選択・移動・最終攻撃で同じ交戦コンテキストを参照し、味方、とくに総大将が直接交戦している時は地形・性格・通常の隊形維持だけを理由に傍観しない。救援時は攻撃用APを固定的に1残さず、川や悪天候で今ターン攻撃できなくても全APを前進へ使える。一方、通常時は従来どおり攻撃APを残して行動し、向き変更後に攻撃する判定では「向き変更AP＋攻撃1AP」を必ず満たす。
- `js/troop_allocation.js` — 兵力・兵科自動配分の正本。野戦前の自動編成では統率＋武勇を主軸としつつ、兵科適性の解釈は `SkillManager` を通して軽く加点し、適性だけで編成を決めない。 **1部隊が率いられる兵数上限と、選択武将数から軍全体の出撃可能兵数を求める計算もここを唯一の正本とする。** 上限値は `GameConfig.War.TroopAllocation.MaxSoldiersPerUnit` だけに置き、プレイヤー出陣・迎撃・自軍/同盟援軍・AI攻撃/迎撃・諸勢力蜂起で `武将数×上限値` 等を個別計算しない。数量UIは説明表示を追加せず、共通Serviceが返す上限までしかスライダー/数値入力を動かせないようにする。
- `js/reinforcement_service.js` — 承諾後の自軍・同盟・諸勢力援軍編成／資源消費の正本。自動・手動とも城在庫の増減をここへ集約する。
- AIが援軍要請を承諾するかどうか（実効確率・大雪・支配関係・拒否可能スキル・最終サイコロ）は `DiplomacyManager.getAIReinforcementAcceptanceInfo()` / `checkAIReinforcementAcceptance()` を正本とし、攻撃側・守備側とも同じ窓口を使う。

`troop_allocation.js` と `reinforcement_service.js` は小さいものの、複数の戦争入口から共通利用され、計算重複防止の役割が明確なため独立を維持します。

## AI・外交・勢力

- `js/ai.js` — AI全体。まだ巨大で、戦争・内政・外交判断の分離候補。兵施し・通常訓練の目標値は通常上限100までとし、戦争由来で100を超えた士気・訓練を不足扱いしたり通常内政で100へ下げたりしない。
- `js/ai_operation.js` — AI作戦。

- `js/diplomacy.js` — 外交。外交効果・AI判断に加え通常外交会話の生成を担当する。会話上の格そのものは `ConversationStandingRules` を正本とし、プレイヤー発の外交・AIからプレイヤーへの外交・臣従コモンイベントは `buildDiplomacyGreeting()` / `getDiplomacyMessages()` を共用する。使者本人の身分差や官位・功績、大名家同士の官位・威信は成功率へ混ぜず、呼称・敬語・要求/返答の柔らかさだけへ反映する。将軍・左馬頭など特殊な公的権威を持つ本人が他家所属の使者になった場合は、主君の名代として自分を下げるのではなく、本人自身がその外交を取り持ち・勧める口調を使う。敵対/友好など現在の外交関係は「格」と混ぜず関係温度として別に扱い、敵対相手には礼を保ったまま少し硬く、友好的な相手には拒否時も角を立てにくい言い回しへ薄く反映する。外交当事者同士が近親者なら、面談と同じ直接会話呼称を優先して『父上』『兄上』『義父上』や年少親族の官位名/諱を使い、敵対中でも血縁呼称自体は崩さず口調だけを冷たくする。歴史イベントの演出台詞は作者が意図した個別演出を優先し、自動で上書きしない。 **基本外交statusと付加関係を分離する。** `changeStatus()` は普通・友好・同盟・支配・従属・和睦・敵対などの基本statusだけを変更し、婚姻 `isMarriage` と人質 `hostageIds` を副作用で消さない。したがって支配/従属→同盟、同盟→支配/従属などの上書き後も婚姻・人質は別軸で維持できる。対外婚姻コマンドは同盟を強制せず、婚姻フラグと大幅な友好度上昇を与え、以後の親善・同盟・降伏勧告・従属願および援軍受諾を姻戚関係として後押しする。ただし、和睦条件として差し出される婚姻は人質・城割譲と同じく和睦の担保として扱い、婚姻フラグは成立させても通常婚姻コマンドの友好度大幅上昇は適用しない。婚姻の成立・死亡・離縁によるフラグ更新は `setMarriageRelation()` / `refreshMarriageRelation()` を正規窓口とする。断交等で実際に敵対へ移った時だけ人質の脱走/拘束と嫁いだ姫の去就を処理し、姫を据え置く場合は敵対中でも婚姻関係を維持する。AIの姫処遇は据置・返還を基本とし、処断は低義理かつ深刻な敵対時の少数例に留める。 和睦の条件交渉は別の事務的確認画面へ切り離さず、使者と当主の会話の中で無条件成立・条件提示・決裂まで続ける。姫・人質・城割譲の候補生成と条件の重さ選択は `DiplomacyManager` 内の共通窓口へ一元化し、同じ候補ロジックをプレイヤー発・AI発・AI同士へ複製しない。AIからプレイヤーへの和睦で条件を求めた際、AIが譲歩できない場合も即座に不自然な決裂台詞へ飛ばさず、無条件和睦へ戻るか交渉を打ち切るかを選べるようにする。 **AI和睦では申込側と受諾側の事情を混同しない。** 申込側の敵対数・戦線圧力は「和睦を申し込む動機」と提示条件を飲む判断に使い、最初の和睦受諾率へ加える多正面補正は受諾側が抱える敵対数を使う。共通敵ボーナスは同盟・従属願の協調判断にだけ使い、和睦受諾率には使わない。これにより別の敵との和睦成立だけを理由に、残る相手との和睦成功率が上下しないようにする。AI同士の通常和睦も、条件を提示できた時点で自動成立させず、申し込んだ側が戦況と条件の重さを踏まえて受諾判定を行う。AIが自発的に通常和睦・朝廷和睦を狙う相手は、現在領地が直接隣接している敵対勢力に限定し、月初計画後に前線が変化した場合も実行直前に再確認する。 **外交会話の結果文は実際に通った交渉段階と一致させる。** 無条件の申し出を即時拒否された場合に「条件が折り合わず」と表示せず、条件提示まで進んで決裂した時だけ条件交渉の決裂として扱う。従属家が主家へ同盟移行を求める場合は、プレイヤー発・AI発とも共通の専用会話を使い、庇護への謝意を示しつつ「主従の約を解いて盟友となる」意思を明示する。 **AI従属家の独立は義理・野望を連続値で使う。** 野望が低いほど独立そのものを考えにくく、野望・主家との戦力差・友好度・従属期間から独立意欲を作る一方、義理が高いほど直接の断交・攻撃を抑え、まず親善または「従属/支配→主従解消・同盟移行」への平和的な関係変更を試みる。格上げは自動成功させず通常の外交受諾判定（相手がプレイヤーなら選択）を通し、拒否された月は従属を維持して後月に再評価する。

を正本としてA/S適性を能力条件とは別の噂理由にできる。適性を噂本文へ出す時は内部ラベルをそのまま読み上げず、足軽は「野戦」、騎馬は「騎馬隊の扱い」、鉄砲は「鉄砲隊の扱い」、弓術・武芸はそのまま、操船は「船の扱い」として世界内の評判へ言い換える。忍術だけは「腕前」「長ける」等の称賛にせず、「何やら、忍びの者を使うことも多いと聞きます」のように社会的な距離を含む伝聞として扱い、話者自身の親族については伝聞にせず「忍びの者を用いることもあります」程度の中立表現にする。候補抽選は条件ぎりぎりより高能力・S適性が少し出やすい軽い重み付けとし、同一面談中は候補を再抽選しない。噂の情報量と口調は面談開始時に固定した表面態度を再利用し、reservedは短く、cold/startledは拒否し得る。通常大名本人が噂対象の場合は、本人が勢力を率いているという自明な立場説明を3段目に重ねず、人物名・能力/適性の2段で終了する。諸勢力武将（頭領本人を含む）は固定忠誠50を通常家臣の忠誠情報として解釈せず、個人引抜・取込・鎮圧・戦力比較・話者との能力比較などの補足を能力/適性の後へ重ねない。人物紹介＋得意能力/適性だけで終了する。通常の他家武将も、能力/適性の後へ『問題なし』『特段悪い話なし』等の意味の薄い忠誠補足を置かない。既存の偽装後の表面段階が danger 以下、すなわち明確に不満を示す段階に入った時だけ、主君との折り合いを粗い噂として1発言追加する。stable / warning は追加発言なしで終了する。reserved は従来どおり口数を抑え、cold / startled は噂自体を拒否し得る。話者→当主の身分・親族・官位・表面態度による最終口調は通常の `_applyIndependentInterviewRegister()` / `ConversationStandingRules` を通す。
- `js/interview_system.js` — 面談の進行・判定・台詞生成の正本。忠誠評価は軍師の警告境界（85以上安定／75～84注意、74以下は危険域）と連動し、危険域以下は60・40・25を境に段階化する。忠誠段階と智謀による偽装自体は `LoyaltyInsightRules` を共用する。本人の自己申告では、智謀70～89なら実際の忠誠評価より1段階、智謀90以上なら2段階だけ高く見せる（上限は安定段階。低忠誠から最高評価へ飛ばさない）。他者評価でも同じ表向き段階を使い、聞き手の智謀・接触度・義理と対象の智謀・野望から情報精度を計算する。高智謀の対象による偽装は、十分な智謀と情報精度を持つ聞き手だけが看破でき、看破時は「表向き」と「本心」を分けた専用台詞を使う。情報精度が極端に低い場合は忠誠を推測せず「内心をほとんど見抜けない」専用台詞へ分岐し、直前の好悪・接触評価を否定しない接続表現にして会話前後の矛盾を避ける。 面談開始時は初回面談による忠誠+1を先に確定してから、現在忠誠・智謀による偽装・義理・野望からその面談中の表面態度を一度だけ決め、最初の挨拶と以後の導入口調へ共通して使う。低忠誠の聞き手に他者評価を頼んだ場合も、自身の不満を固定台詞で自動露呈させず、その面談で確定した表面態度と通常の情報精度判定に従う。観察者視点の『目を合わせない』『危険な気配』などを本人の台詞として出さず、言い淀み・短い返答・過剰な丁寧さなど本人の発話だけで態度を表現する。これらの調整値は `GameConfig.Main.Interview` を正本とし、85/75の境界は `GameConfig.Main.Gunshi` から導出する。 他者の忠誠評価には、相性差1につき1を基礎とする悲観バイアスを加え、革新性の差と聞き手の野望で悪化させる一方、聞き手自身の忠誠・義理・主君との相性が高いほど私情を抑える。逆に、聞き手自身の不満段階・義理の低さ・主君との相性/革新性の不一致が大きく、対象とは相性/革新性が近く、対象も不満を抱えているように見える場合は、固定忠誠値ではなく段階点の積み上げで最大2段階だけ好意的に評価する庇護バイアスを持つ。庇護時も「同志」など自分や対象の低忠誠を露呈する台詞は使わず、表面上は客観的な擁護として話す。情報精度が不足している場合は真の忠誠を漏らさず、偏見が強い場合だけ根拠の薄い警戒または擁護として表現する。表面態度が cold / startled まで落ちている武将は、他者についてだけ急に長広舌にならず、原則一言で濁し、敵視・庇護が強い相手だけ短い悪評／擁護を返す。reserved も接触説明を省いて要点を二言以内にする。『方針について』は統率・武勇・内政・外交・智謀のうち本人の高い能力から最大2分野を選び、統率は実作戦の攻撃先、武勇は訓練・士気、内政は `AIDomesticPriorityRules` の城壁修復／石高開発／鉱山開発、外交は既存外交優先、智謀は既存の調略目標・引抜判定を参照して話す。一般武将は主に所属城・所属軍団、軍団長は軍団全体、軍師は勢力全体までを見られる。軍師は智謀が高くなりやすいため、智謀が他の主要能力の最高値より1.2倍以上突出している場合だけ智謀分野（調略）を候補にし、毎回調略の話へ偏らせない。開示量は忠誠・義理で変え、面談専用の別AI判断は作らない。連続会話では呼びかけ・相槌・『軍団長として』等の立場前置きを各メッセージへ機械的に重ねず、導入は系列の最初だけに置く。前文で説明済みの信頼関係・接触頻度も後続文で繰り返さない。他者評価の3段階（人物評価→接触関係→忠誠所見）は各段の評価方向を比較し、好意的な人物評価から接触が薄い中立域へ移る場合も軽い逆接として「ただ」を許可する。忠誠を全く読めない状態は neutral と混同せず unknown として扱う。接触が十分あり人物像を知っている相手の本心だけ読めない場合は「ただ、～本心までは」で一段深い未知を示し、接触が十分でない相手は「正直なところ、～本心は」で判断材料そのものが乏しいことを示す。他者について聞く時の社会的な言及は `ConversationStandingRules` を共用し、家中身分・官位の上下・功績差を呼称（例：官位名、左馬頭様、公方様）・三人称・実績への一言へ薄く反映する。 他者の忠誠段階そのものは `LoyaltyInsightRules` のまま変えず、会話上の言い方だけを関係別にする。通常家臣は「忠義・忠節」、当主の一門は「殿のお考えへの理解／食い違い／思うところ」、将軍・左馬頭は「理解／協調／慎重な所見」を用い、「殿との距離ができた」のような俯瞰的な人間関係説明は避ける。同じ家中の人物を『存じております／存じ上げております』と紹介する定型句は使わず、呼称の直後から人物評価へ入る。また質問者である当主と対象に `realFatherId` で確定できる実父系血縁があり、対象が無官なら『御父君』『御子息様』『御兄君』『御舎弟』『御祖父君』『お孫様』のように質問者から見た続柄を第三者の言及へ使う。答える本人と対象の間に近親関係がある場合はそちらを最優先する。`adoptiveFatherId` の直接参照は女性なら『母上』、男性なら『義父上』、実父系では父・実兄・祖父を『父上』『兄上』『祖父上』、実弟・実子・実孫は官位持ちなら敬称なしの官位名、無官なら敬称なしの諱で呼ぶ。近親者については後続の人物評価・接触説明も『あの方とは』等の第三者的な言い回しを避け、関係を前提にした自然な文章へ切り替える。無官の軍師は当主・話者双方の一門でない場合のみ『軍師殿』とする。面談相手本人から当主への直接呼称は `ConversationStandingRules` の直接会話呼称を使い、子・弟・孫から年長親族へは『父上』『兄上』『祖父上』等を官位より優先する一方、実父・実兄・実祖父や義父/武将母など年長側から年少親族へは官位名または諱を敬称なしで呼ぶ。さらに面談時の家族距離も `ConversationStandingRules.getInterviewSpeakerPosture()` を正本とし、当主の父・祖父・実兄・武将母・義父は `senior_close`、伯父・叔父は `senior_extended` として、忠誠による表面態度を保ったまま通常家臣より親しい挨拶・メニュー導入・本人返答へ切り替える。似た台詞を忠誠段階ごとに無理に増やさず、親しい／平常／よそよそしい程度の意味のある差へまとめる。血縁がない場合でも、将軍・左馬頭（将軍候補）は通常官位ランクより先に特殊権威として `higher_court` へ入り、その他の人物も本人の官位が当主より上なら同じく伯父・叔父に近い一段上位者らしい面談口調を許す。左馬頭は通常官位としての `rankNo` が当主より低い場合でも通常家臣口調へ落とさず、他官位を併有していても特殊呼称は実際の候補官位IDから『左馬頭様』を優先する。これらは外交成功率や忠誠値等のゲーム判定には混ぜない。当主の父・祖父・実兄等が他の家臣を評する際も、対象が本人より明確に格下なら『柴田か』『信頼しておる』等の家中年長者口調を使い、高官・特殊権威を持つ相手には既存の格式判定を優先する。さらに `senior_close` / `senior_extended` / `higher_court` の話者は、挨拶だけでなく『調子はどうだ』の思想回答、『方針について』、『武将の噂』、他者評価の人物評・接触説明・忠誠所見まで同じ面談会話レジスターを通し、途中だけ『ございます／おります／申し上げる／でしょう』等の一般家臣敬語へ戻さない。特に他者評価では『誰に話しているか』と『誰について話しているか』を別軸にし、父・祖父・兄などが子である当主へ軍師・国主・高官を語る場合も、対象への敬意は『軍師殿』『あのお方』等の呼称・三人称へ残しつつ、聞き手への文末は常体のまま保つ。将軍・左馬頭を第三者が評する場合は呼称だけでなく人物評価・接触説明も高敬意の専用内容へ切り替え、相性が悪くても特殊権威そのものを軽んじる表現にはしない。 功績差を匂わせる場合も、将軍・左馬頭には通常家臣向けの『その働きは、家中でも～』を使わず、『家中の皆も、あのお方には一目置いております』のように本人の格式と周囲の敬意を示す表現へ切り替える。 また、質問者である当主の父・祖父・実兄・武将母・義父など年長近親者に功績差がある場合も、通常家臣を査定する『働き』表現は避け、家中での重み・言葉の重さとして匂わせる。伯父・叔父は一段控えめに『家中の皆も一目置く／頼りにされる』程度とし、子・弟・孫など年少親族は通常の功績表現を使ってよい。左馬頭・将軍など `higher_court` の本人返答では『当家に身を置く以上』のような一般家臣としての所属意識を強く出す定型句を使わず、高格式者として務めを引き受ける言い方にする。低い表面態度でも近親者への導入は『父上について、ですか』のような第三者的構文にせず『父上ですか』と直接受ける。無官の通常呼称も同ルールを正本とし、原則は「姓＋殿」、話者と対象が同姓なら一門関係に限って「諱＋殿」を許可し、同姓でも一門でなければ距離感と識別性を保つため「フルネーム＋殿」とする。加えて『他者について』で質問者の当主と対象が同姓なら、話者が異姓でも「織田殿」のような曖昧な姓呼びを避け、血縁続柄・官位・軍師等の優先呼称がない限り「織田広良殿」のようにフルネームで呼ぶ。忠誠・相性・接触度の判定内容は社会的な格で改変せず、功績も数値としては表示しない。「までは」は手前の情報を知っている場合だけ使う。「ただ／もっとも／正直なところ」は各素材文へ固定で埋め込まず系列全体で管理し、1段目本文中ですでに逆接を使っている場合も含め、3段の中で明示的な逆接は原則1回までとして「ただ、…」の連続や前後にそぐわない接続を避ける。『調子はどうだ』はまず忠誠に基づく現在の心境を表面態度に応じた口調で答え、その後に必要なら革新性という本人の価値観を独立した次メッセージとして表示する。革新性の前に『それと』『加えて申し上げるなら』等の機械的な接続詞は付けない。面談での革新性分類は勢力詳細の表示に合わせて33以下＝保守、34～66＝中道、67以上＝革新とする。内部の忠誠段階は偽装・軍師評価のため維持するが、面談会話では serious / critical を同じ拒絶系として扱い、深刻以下で『特に申し上げることはございませぬ』等と会話を拒絶した場合はそこで終了して価値観の話を続けない。連続する文で同じ相槌・呼びかけ・接続詞・立場前置きを重ねない。

- 自作JSがHTMLを生成する場合、`style` 属性はゲージ幅・文字縮尺など実行時のCSS変数（`--xxx`）だけを許可する。静的レイアウトはCSSクラスへ置く。
- 画像エラーやクリック等のイベントは `onclick` / `onerror` 属性ではなく、生成後のイベント登録または既存のイベントデリゲーションを使う。
- 国主評定は `index.html` が一覧・命令モーダルの固定DOM構造、`style.css` がPCは16:9（1280×720）の左右対面配置、スマホは9:16の2列×4段配置を担当し、物理ウインドウ差は既存の等比縮小・黒帯処理へ委譲する。`legion_council_view.js` は表示と一時編集、`legion_policy_system.js` はゲームルールを担当する。評定一覧には命令UIを直接置かず、軍団カード全体から別命令モーダルを開く。一覧下側には詳細情報画面と同系統の補助操作帯を置き、右下の［一括］から全軍団用の一括命令を開く。評定一覧・命令画面はいずれも固定ゲーム画面内に収めてスクロールさせず、スマホの2列×4段はカード行を固定高にし、端末幅によって9:16論理画面が高くなってもカード自体やカード内の文字配置を縦に引き伸ばさない。将来命令項目が増えて一画面に収まらない場合はタブまたはページ分割で拡張する。観戦へ移行した勢力は保存済み評定方針を保持するがAIは拘束されず、観戦からプレイヤー操作へ戻した時にその勢力の保存方針を再適用する。直轄軍団0のAI作戦だけは操作主体切替時に `AIOperationManager` が生成/破棄を整理する。

`selector_modal_view.js` は小さいものの、複数情報画面の初期化漏れを防ぐ共通Viewなので独立を維持します。


## ローディング・低メモリ端末

- ローディング表示は飾りの無限アニメーションではなく、`DataManager -> GameManager -> UIManager` の進捗通知で現在段階と割合を表示する。`prefers-reduced-motion` でも進捗文字とバー幅は更新される。
- 月末・月初などプレイヤー入力を受け付けない長い月次処理では、新しいオーバーレイを増やさず既存の `#ai-guard` を共通待機表示として再利用し、「月末処理中...」「月初準備中...」のように現在段階を明示する。会話・イベント・カットインは既存の上位レイヤーを優先し、処理再開後はAI進捗表示へ自然に戻す。
- 3140×2440級の色コード画像は全画面Canvasへ複製して長時間保持しない。`DataManager.scanImageByStrips()` がPCは128行、スマホは32行単位で読み取り、帯ごとにブラウザへ制御を返す。城色画像は種点座標だけを取得し、国IDマップ上で城領域を構築する。これにより古いスマホでもローディング画面の描画・OS監視・GCの機会を確保する。
- 城ID・国IDは現シナリオの最大IDに応じて最小のTypedArrayを選ぶ。現行1560シナリオでは双方 `Uint8Array` で、1pixel=1byte。`UIManager`、`EventMapEffects`、台風判定は同じ配列を共有する。城領域構築時には各城の外接矩形も同時に小さな配列へ記録し、戦闘点滅のたびに地図全766万pixelを走査し直さない。
- スマホの勢力色・地方/勢力ハイライトなど全画面Canvasは内部解像度を縦横1/2（面積1/4）にし、CSSで地図サイズへ拡大する。雪Canvasはさらに低解像度で保持し、AI開始時の一時資源解放対象にはせず、表示状態を維持したままメモリ量を抑える。描画時も巨大ImageDataを一枚作らず32行程度の帯へ分割する。城・国の判定用IDマップ自体は正確な当たり判定のため原寸を維持する。
- 勢力色の塗りは黒線の手前に微細な隙間が出ても、単純な膨張で隣接領域へにじませない。描画pixelが覆う元マップ領域を勢力ID単位で確認し、そこが完全に0の場合だけ外周1 source pixelを参照する。外周の非0候補が同一勢力で2pixel以上ある場合だけ補完し、異なる勢力が混ざる境界や支持1pixelだけの場所は補完しない。補完済みpixelを次の補完元には使わないため、2px・3pxと連鎖膨張させない。
- 表示専用の日本地図はスマホだけ75%解像度の `japan_map_mobile.png` を使う。論理座標と判定用IDマップは原寸のままなのでゲームルールには影響しない。CSS背景から原寸地図を二重ロードせず、常駐する1枚のImage要素を正本とする。
- 新規開始・セーブロードでは、城/国IDマップの構築完了だけでロード終了としない。`UIManager.prepareMapBaseImage()` で実際に表示するPC/スマホ用Imageのload/decode完了を待ち、`renderMap()` と最初の描画フレームまで終えてから `global-loading-screen` を閉じる。ゲーム画面を先に露出させて地図だけ後から表示しない。
- 武将一覧・詳細などで背景更新を止める時、スマホでは地方・キープ光など一時Canvasを解放し、城カードのdrop-shadow/animationも停止する。雪は気象状態を表す継続レイヤーなので解放対象に含めない。復帰時の勢力色Canvasは1pixelだけで健全と判定せず、実際の領土内にある拠点種点から地図全体へ分散した複数点を1x1 readbackで確認する。一部でも透明化していればhashを無効化して全描画する。さらに低メモリモーダル・全画面戦闘など `display:none` をまたいだ復帰、およびOS/ブラウザの非表示→再表示では、contextlostが通知されずcompositor側だけ部分欠落する端末を考慮してhash一致を信用せず1回だけ全描画する。backing store自体は正常でgetImageDataでは異常を検知できないcompositor白抜けについては、表示地図Image・勢力色Canvas・雪Canvasを同じDOM/同じ兄弟位置のまま付け直して合成面だけ再提示し、巨大pixelの再計算を毎回行わない。結果画面のように背景復旧後に覆いを外す画面は、次の描画フレームでもこの軽量復旧を通す。同一シナリオの `renderMap()` で静的層を再利用する画面切替も同じ再提示を行い、hash一致のCanvasを白抜け状態のまま使い続けない。Canvasの `contextlost/contextrestored` も同じ復旧経路へ接続する。
- 武将一覧などの仮想スクロールは、詳細画面への遷移・別一覧への切替・モーダル終了時に旧scroll handler、遅延timer、分割描画を必ず停止し、非表示DOMのクロージャから大量データを参照し続けない。武将・拠点・勢力・国のID索引は `GameManager.getBusho()` / `getCastle()` / `getClan()` / `getProvince()` が保持する正本を利用し、一覧再描画ごとに同内容の大規模 `Map` を複製しない。拠点内の武将・浪人数は全武将配列を毎回走査せず、現行所属の正本である `Castle.samuraiIds` を `getCastleBushos()` 経由で参照する。スマホの仮想スクロールは表示外バッファと行HTMLキャッシュを画面内行数に合わせて抑え、見た目・並び・操作を変えずDOM再生成と一時メモリを減らす。
- 特定大名家の武将候補を繰り返し求める処理は、全武将配列をその都度 `filter/find/some` せず `GameManager.getClanBushos()` の勢力別索引を共用する。索引へ保存するのは `busho.clan` による所属だけとし、死亡・未登場・活動状態・軍師/国主など変動する状態を焼き込まない。所属変更は唯一の書換窓口 `AffiliationSystem.setClanIdRaw()` が `bushoAffiliationVersion` を進めて索引を無効化する。返される所属配列は共有索引なので呼び出し側から `sort/splice/push` 等で直接変更せず、変更が必要な処理だけ `slice()` して使う。
- 国・地方単位のAI目標探索は、全拠点を走査しながら各拠点の国を再検索せず、シナリオ中に変わらない `provinceId` / `regionId` だけを `GameManager.getProvinceCastles()` / `getRegionCastles()` / `getRegionProvinces()` の静的索引へまとめる。所有勢力・兵数・外交関係など変動する状態は索引へ含めず、取得した少数候補へ毎回最新値を判定する。姫のID参照も `getPrincess()` の共通ID索引を使い、一覧・婚姻処理から同じ配列を毎回 `find()` しない。
- 全件走査を索引・限定候補へ置き換える最適化は、元の候補条件と完全に同値であることを先に確認する。未知ID・無所属・未登場・死亡などを便宜上0へ丸めて候補を広げたり、逆に在城名簿・活動中一覧だけへ狭めて旧処理が見ていた対象を落としたりしない。特に共有索引は参照元配列の追加・所属/所有変更でも無効化されることをテストし、同値性を保証できない低頻度処理は全件走査のまま残す。
- UIの1回の同期描画内だけで同じ配列所属判定・外交関係を何度も参照する場合は、`Set` / `Map` の短命ローカル文脈へまとめてよい。長寿命キャッシュへ昇格させず、`includes()` と同じ比較意味・現在の外交状態・候補順を変えない。勢力色Canvasのように変更versionが専門Setterで保証されている状態は、全件を文字列化したhashを毎回生成せずversionを再描画判定に使う。
- 同一コマンド判定やAIの一連の行動ループ中に変化しない事実は、同じ条件式を各候補ごとに繰り返さず1回だけ計算して共用してよい。ただし、候補集合を狭める必要はなく、型の厳密一致・未登場・死亡・所属外など旧条件に意味差がある場合は元の全件条件をそのままループ外へ移す。所有・所属・生死・役職等が途中で変わり得る処理は事前固定しない。
- 年初の姫生成のように、同じ厳密条件を勢力数ぶん繰り返す処理は、その処理中に候補元の所属・活動状態が変化しないことを確認した場合だけ1回の文脈集計へまとめてよい。旧条件が `===` ならMapキーもNumber化せず生値を使い、元配列の順序を保つ。逆に武将登場処理の一門探索のように、先に処理した人物の登場・所属変更が後続人物の候補へ影響する処理は事前固定しない。
- `castle.ownerClan` と `busho.clan` は所有・所属索引の無効化versionと一体なので、実行時の直接代入を禁止する。城所有者は `CastleManager.setOwnerIdRaw()` / `changeOwner()`、武将所属は `AffiliationSystem.setClanIdRaw()` 等の専門窓口を必ず通し、各窓口がversionを進める。この境界は回帰テストで全JSを監査し、索引が古い所有・所属を保持する経路を作らない。
- 新規シナリオ・セーブ復元・タイトル復帰では、旧シナリオの検索Map・勢力別索引・国地方索引を `releaseScenarioDataIndexes()` で先に切り、地図TypedArrayの解放と同じ切替境界で処理する。`MapGraphService` の隣接Mapも旧 `castles` 配列を保持するため同時に `invalidate()` し、UIの会話顔画像先読みなど再生成可能な短命キャッシュも切替時に解放する。セーブ復元では旧 `turnQueue` のCastle直接参照も新データ生成前に破棄し、新旧シナリオの大量オブジェクトを同時に保持する時間を短くする。
- 経路探索中の外交通行可否のように、1回の同期探索中には変化せず同じ勢力へ何度も問い合わせる値は、その探索呼出しのローカルMapだけで再利用してよい。ターンや別探索をまたぐ永続キャッシュにはせず、候補城・探索順・目標到達判定は変えない。不正な勢力IDは有限数へ正規化できない場合キャッシュせず、別々の生値を同一候補へまとめない。
- 地図の道路SVGのように、シナリオ中に変化しない城座標・隣接関係・海路関係だけから作るDOMは `renderMap()` ごとに再生成せず静的描画層として再利用する。所有勢力・兵数・外交・選択状態など変動値は静的層へ含めず、シナリオ/セーブ切替時は旧 `castles` 参照とDOMを `releaseScenarioTransientCaches()` で必ず解放する。
- PC向け顔画像のアイドル先読みは少数batchに限定し、シナリオ切替時に世代tokenを進めて旧予約を無効化する。`requestIdleCallback` / `setTimeout` の古い予約が発火しても旧シナリオの次batchを開始せず、新旧画像デコードを長時間並走させない。
- 端末別に常時非表示となる旧UIコンテナへ、表示中と同じ顔画像・情報DOMを複製しない。PCでは `#pc-new-status-panel`、スマホでは `#mobile-top-left` の実表示側だけを更新し、画面切替時は反対側の残存DOMを空にする。拠点一覧など同一モーダル内のタブ・ソートで不変な集計は、そのモーダルのライフサイクル内だけキャッシュし、画面を新しく開く時に破棄する。
- 諸勢力のID・所在拠点検索は `KunishuSystem` 内の索引を正本として再利用し、地図描画の各拠点ごとに全諸勢力を走査しない。壊滅状態は既存オブジェクト上で変化するため、拠点別索引から得た少数候補へ局所的に `isDestroyed` を判定する。諸勢力データの差し替え・追加時は索引を無効化または再構築し、状態変化を古いキャッシュで隠さない。
- 共通リストのイベント委譲は古いAndroid WebViewでも動く基本イベント情報だけを渡し、`Proxy` のように実機世代で対応差の大きい機能を必須経路へ置かない。一覧→詳細では、履歴に復元条件を保存した後、詳細DOM生成前に旧一覧DOM・画像参照・保留中の描画フレーム・再生成可能な一覧キャッシュを解放して、新旧画面の瞬間メモリを重ねない。
- AI連続進行中もスマホの城カードのfilter/animationを抑え、非必須地図Canvasを解放してGPUメモリの余裕を作る。戦闘点滅・制圧演出は対象城周辺だけの切り抜きCanvasを必要時に作る。
- **野戦・攻城戦の全画面戦闘中は、スマホで背面の通常地図を compositor の対象から外す。** 戦闘画面は通常地図と同時に見ないため、`UIManager.suspendMainMapForBattle()` / `resumeMainMapAfterBattle()` を正本として背景更新を止め、スマホだけ `#map-scroll-container` を一時的に `display:none` にする。野戦・攻城戦が連続・重複しても早く背景を復帰させないよう所有者を管理し、各戦闘Systemから独自に地図表示を上書きしない。PCは背面地図の表示を維持してよい。
- **戦闘のUI更新は「値が変わったDOMだけ」を触る。** 野戦では部隊DOM参照と直前にハイライトしたHEXをキャッシュし、毎行動で全HEX走査・全アイコン検索・部隊ごとの`<style>`再生成を行わない。非表示の軍勢詳細は情報画面を開いた時だけ構築する。攻城戦も顔画像・能力HTML・援軍カード等を毎行動で無条件に再代入せず、同値ならDOM変更を省略する。これらの最適化で戦闘計算・AI判断・乱数系列を変えない。
- **PC地図ドラッグの保留描画を終了操作後に適用しない。** `mousemove` は1フレーム1回へ間引くが、`mouseup` / `mouseleave` / `resetMapViewState()` では保留中のrAFを取消し、次の操作に `isMapTicking`・ドラッグ中フラグ・掴みカーソルを残さない。旧画面の描画予約は既存の `_mapViewResetToken` も照合して新しい地図へ反映しない。ドラッグ中の正常なスクロールとPC慣性は維持し、画面ごとの独自タイマー・世代管理を増やさない。
- **地図のズーム入力と画面寿命は `UIManager` の地図Viewを正本にする。** PCズームのrAFは既存 `_mapViewResetToken` によって失効させ、`resetMapViewState()` がアニメーション入力ロックをその場で解除する。失効した古いrAFが後発ズームのロックを解除してはならない。ホイール／ピンチの操作間隔は `_beginMapZoomCooldown()` の単一timerで管理し、地図のリセット時に旧解除予約を破棄する。画面・端末ごとの追加タイマーや新しい世代管理を増やさない。
- 1月の全武将能力再計算はスマホ128人単位、AI月次作戦は複数軍団ごとにブラウザへ制御を返し、長時間の同期CPU占有を避ける。実機診断は対象城を伴う処理だけキュー位置を記録し、月次・イベント・画面操作へ古いAIキュー番号を持ち越さない。武将一覧などの共通情報画面では `ui:modal:<pageType>` を残し、寿命処理段階・作戦処理中勢力と同様に次回の実機切り分けへ使う。
- 一門関係の正本は `realFatherId` / `realMotherId` / `adoptiveFatherId` / 配偶者IDなどの関係データとし、CSVの旧 `familyId` 列は廃止する。
- `baseFamilyIds` / `familyIds` は入力値・保存値ではなく `js/family_system.js` の `FamilyLinker` が毎回ゼロから再構築する派生キャッシュとする。養子・婚姻イベント側から配列を直接pushしない。
- **夫死亡・婚姻解除後の未亡人帰還先の探索は、変更済みの `husbandId` を反映した家系キャッシュを使う。** 特に実家滅亡時の親族探索は古い姻戚を候補に混ぜないため、婚姻解除→ `FamilyLinker` 再構築→候補探索の順序を守る。独自の系図解決や新しい正本は追加しない。
- `baseFamilyIds` の実父・養父連結はUnion-Findで一度に構築し、関係変更後の再構築で古い一門IDが残らないようにする。
- 派生キャッシュはセーブデータへ保存せず、ロード後に関係データから再構築する。4,000人超の重複配列を保存しないことでセーブ容量と一時メモリを抑える。
- 現行データでは `Busho` / `Princess` の生成時と `FamilyLinker` が `baseFamilyIds` / `familyIds` を必ず構築するため、全人物の親族配列再正規化を月初・月末・死亡処理では行わない。
- セーブ一覧用の勢力図は最初から1/4サイズの専用白地図へ直接描画し、サムネイルのために3140×2440の中間Canvasを作らない。
- タイトル初回表示では大画像・大量顔画像・音声を同時プリロードしない。**シナリオ開始・セーブ復元の共通ロード幕**では `GameManager.prepareGameAssets()` を待ち、全顔WebP・小型共通アイコン・短尺SE・PC用圧縮BGMを段階的に準備する。大地図解析、顔画像decode、音声decodeを一度に重ねず、少数batchと描画機会を保つ。PCの顔Image保持とスマホの保持枚数上限、PC BGMの圧縮取得と全曲PCM常駐回避を守る。

## テストとバランス検証

- `tests/run_tests.js` — 本体ロジック・設計境界の回帰テスト。
- `tests/run_visual_tests.js` — Chrome系ブラウザで主要UIを実描画し、寸法・突破領域・隣接領域への侵入を検査するレイアウト回帰テスト。
- `tests/visual/` — ビジュアル回帰用の固定フィクスチャ。ゲーム本体のCSSを読み込んで検査する。
- `tools/simulation/player_focus_sim.py` — 大量試行による簡略バランスシミュレーション。

通常テストは「ロジック・設計境界が正しいか」、ビジュアルテストは「実ブラウザ上のレイアウトが崩れていないか」、シミュレーターは「バランス傾向がどうなるか」を担当し、目的を混ぜません。

## 継続開発の整理方針

特定の旧Roundを固定の基準版にはせず、現行仕様を正本として「整理するための整理」は行いません。

- `TurnManager`、`CommandSystem` は現在の責務境界を維持し、行数だけを理由に追加分割しない。
- `war_effort.js` / `field_war.js` / `diplomacy.js` / `ai.js` は大きいが、全面分割は新機能や大規模改修で具体的な必要が生じたときだけ行う。
- 同じゲームルール・計算・重要状態変更が複数箇所に現れた場合は、その重複だけを既存のRules/System/Serviceへ戻す。
- CSSは実際の競合・表示崩れを発見した周辺だけ整理し、機械的な大掃除はしない。
- 既に整備した設定、技能、所属、城所有権、武将状態、モデル境界、UI分離は自動テストで維持する。
- 大規模な構造変更より、機能追加・バグ修正・バランス調整を優先する。

## 小さいファイルを統合しない判断

現時点で `game_math.js`、`stat_presenter.js`、`selector_modal_view.js`、`troop_allocation.js`、`reinforcement_service.js` は比較的小さいですが、いずれも複数部署から参照される明確な境界です。単に行数が少ないことを理由に巨大ファイルへ戻しません。

一方、起動時固定ボタンだけを担当していた旧 `ui_bindings.js` は単独責務が小さかったため、フォント・viewport初期化と合わせて `app_bootstrap.js` に統合しました。

- 国主評定の二択命令はユーザー設定と同系統の汎用 `.ui-toggle-btn` 表現を使い、未選択は茶系、選択中だけ金色で強調する。確定/戻る等の標準モーダル操作は共通フッター間隔と共通SEに委譲し、個別に重ねてSEを鳴らさない。 面談・評定の本文/補助情報は武将詳細の可読性を下限の目安とし、固定画面へ収めるためだけに7px級など極端に小さい文字へ縮めない。

- 評定内の「一括」は勢力詳細・拠点詳細の右下操作と同じ `.daimyo-detail-action-btn` を再利用し、評定専用CSSは配置だけを担当する。
