# 戦国覇道 マニュアル運用規約

> **この文書はマニュアル自体の変更手順を定める。** ゲームの仕様・禁則・正本の判断は必ず [現行マニュアル](../../ARCHITECTURE.md) を優先する。ここへゲームルールをもう一度書かない。

## 1. 一度だけ決める正本と資料の寿命

| 資料 | 役割 | 更新のしかた |
| --- | --- | --- |
| [`ARCHITECTURE.md`](../../ARCHITECTURE.md) | **唯一の現行開発規則の入口**。最優先の禁則・設計責務・不変条件・例外 | **当該節を直接修正**。新規履歴・日付別追記を冒頭に積まない |
| [`rule_registry.json`](rule_registry.json) | 重要な現行規則の安定ID・担当領域・探索用の短い手掛かり。**本文の複製ではない** | 新しい重要規則を追加するとき、または統廃合したときだけ変更する |
| [`TECHNICAL_REFERENCE.md`](TECHNICAL_REFERENCE.md) | r767時点の詳細部署・API索引と旧規則の原文。現行実装での有効性は別途確認 | 当該領域を読む。原文保全部分は変更せず、現在の追加仕様は別資料か現行マニュアルの当該節に記す |
| [`docs/audits/README.md`](../audits/README.md) | **履歴の所在**。最新版ルールの代用にしない | 一件の監査につき短いリンクを追加。古い評価の訂正はそのリンク注記も更新 |
| [`docs/audits/archive/`](../audits/archive/) | 当時の原文・撤回済みの判断 | **内容を後から書き換えない**。訂正は新規監査記録に残す |
| 現行コードと管理Excel | 現在の挙動と管理データの正本。規則への適合を検証する対象 | 実装があることをもって規則に自動昇格させない |

**指示の優先順位：** 最新の明示的なユーザー方針 → 現行マニュアルの必須規則と、対象領域に適用する現行の詳細契約 → コード・管理データによる実態確認 → 過去の監査記録。矛盾があれば旧規則を黙って採用せず、根拠・到達性・ユーザーの意図を照合する。過去の記録は「現在そうすべきだ」という命令ではない。

## 2. 改修ごとの変更手順

1. **対象の判定：** まず実プレイで到達できる問題か、単なる好み・人工境界かを確認する。ルール変更の必要がなければマニュアルは無変更とする。
2. **責務の特定：** [現行マニュアル](../../ARCHITECTURE.md)の対象節と、必要に応じて技術リファレンス・実装・関連監査記録を読む。ルール本文の正本を一つにする。
3. **同一概念を検索：** 既存の規則・例外・撤回履歴を探し、**追記より既存条文の置換・統合**を優先する。別分野の原則を無理に一つへ統合しない。
4. **優先順位・例外：** 変更する規則が絶対禁則か、通常原則か、限定条件付きの例外か明記する。一般則を改めず例外を追加するときは適用条件を限定する。『前提・対象・結果』を短く書き、開始時/処理途中などの区別を落とさない。
5. **重要規則の識別：** 既存の `<!-- RULE:ID -->` は、条文を編集しても**同じ論点であれば維持**する。別規則へ使い回さない。新規必須規則を増やすときのみ一意のIDを発行し `rule_registry.json` と揃える。新旧条文を両方『現行』として残さない。
6. **古い判断の訂正：** 履歴原文は変更せず、新しい監査記録に「従来の判断・撤回理由・現在の扱い・影響範囲」を記す。現行マニュアルの本文と『取り消された旧前提』表を、必要な場合だけ更新する。表を版ごとの日記にしない。
7. **検証：** `python tools/check_manual.py` を実行し、参照リンク・重要規則ID・原文保全を検証する。関連ロジックテストも実施。**機械検査は意味上の矛盾まで保証しないため、人手で優先順位と例外を読む。**
8. **報告と配布：** 変更ファイルを追加／更新／削除で列挙し、規則の変更か構造整理だけかを区別する。文書のみの変更でゲーム版番号を上げない。失敗・未実施検査を成功扱いしない。

## 3. 増殖を防ぐチェック項目

- **同じ内容の本文を2か所へ書かない。** 正本側には規則本文、他方にはリンク・担当・特有の補足のみを置く。
- **常に短くすることを目的にしない。** 例外・主体・時系列・禁則を省略して誤解が生じるなら、正本を明確に記述する。
- **優先順位の誤昇格を防ぐ。** 以前に撤回された修正、未検証の予測、人工境界テストの成功は、現行ルールの証拠にしない。
- **監査記録は当時の事実。** 旧報告が誤っていた場合も、元資料は保持し、後の訂正記録へ参照させる。
- **部署名・API名は実装と照合する。** ファイルを細かく増やすための分割、不要な互換ラッパー、二重正本を正当化しない。
- **更新が必要な資料だけ更新する。** 何も変わらなければZIP・パッチ・報告書を形式的に生成しない。

## 4. 定期的に確認すること

改修時は対象領域の規則と関連履歴を照合する。一定期間の節目や再監査時には、`ARCHITECTURE.md` 全体と `rule_registry.json`、索引リンク、原文復元検査を通読・実行する。

`tools/check_manual.py` は次を自動確認する：

- `RULE` ID の重複・欠落・未登録、IDに対応する短い手掛かりと正本中の実文の一致
- 現行マニュアル・管理規約・技術リファレンス・履歴索引の相対リンク
- 旧マニュアルの4区間の原文が再構成でき、SHA-256が基準と一致すること
- 正本と歴史資料の区別に必要なラベル

**自動検査で防げないもの：** ユーザーが仕様を変更したのに旧記述を据え置いた、意味が似ているが条件が違う2規則が矛盾する、技術リファレンスのAPIが新実装とずれた、ゲームの実分岐に未検証がある、といった問題。これはコード確認と人間の判断で監査する。
